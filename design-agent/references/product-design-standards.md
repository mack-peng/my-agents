## 一、问题分级（P0–P3）

审查报告和 Spec 的 `Problem` 表统一使用以下优先级：

| 级别 | 定义 | 典型例子 | 处理建议 |
| --- | --- | --- | --- |
| **P0** | 阻断核心任务，或造成严重流失/合规风险 | 支付无法完成、登录死循环、隐私数据泄露、关键页面 404 | 必须修复，进入 Spec |
| **P1** | 明显影响核心路径/转化/可访问性 | CTA 不可见、表单错误无提示、移动端横向滚动、对比度不足 | 应修复，进入 Spec |
| **P2** | 局部体验问题，不影响主路径 | 空状态缺引导、间距不一致、次要文案含糊 | 排期修复 |
| **P3** | 优化项/一致性/品牌细节 | 图标风格不统一、hover 动效缺失、可选的视觉打磨 | 观察或低成本顺手修 |

判断顺序：**用户能否完成核心任务 → 是否影响转化/留存 → 是否影响可访问性 → 是否影响品牌一致性**。

## 二、审查评分表（可选）

需要给整体健康度打分时，每个维度 1–5 分，1 = 严重缺失，5 = 行业优秀：

| 维度 | 1–5 | 评分依据 |
| --- | --- | --- |
| 视觉一致性 |  | 色彩/字体/间距/组件是否成体系 |
| 交互完整性 |  | 核心路径是否有断点，状态反馈是否齐全 |
| 转化路径 |  | 价值主张、CTA、信任信号、联系路径 |
| 品牌表达 |  | 定位、调性、内容活跃度是否一致 |
| 可访问性/性能 |  | 键盘/对比度/alt/CWV/Lighthouse |

评分只用于沟通优先级，不替代逐条证据；评分必须在报告中写明依据。

## 三、产品设计流程（Atlassian）

产品设计是“发现问题 → 创造方案 → 交付价值”的完整闭环：

```
用户研究 → 定义问题 → 构思方案 → 原型 → 测试 → 发布 → 迭代
```

### 核心原则

| 原则 | 含义 |
| --- | --- |
| **Problem-first** | 先搞清楚“要解决什么”，不要直奔方案 |
| **跨职能协作** | 设计、工程、产品一起参与，不是设计丢墙 |
| **验证驱动** | 每个假设通过用户测试或数据验证 |
| **迭代思维** | 产品没有“做完”的那天 |
| **价值导向** | 功能是手段，用户价值是目的 |

## 四、设计规范必备要素（人人都是产品经理）

设计规范是团队的“通用语言”，必须定义清楚：

| 要素 | 内容 |
| --- | --- |
| **色彩系统** | 品牌色、辅助色、功能色（成功/警告/错误）、中性色阶 |
| **字体系统** | 字族、字号层级、字重、行高 |
| **间距系统** | 基准网格（4px/8px）、内外边距规则 |
| **组件库** | 按钮、输入框、卡片、弹窗的状态（默认/悬停/禁用/加载） |
| **图标系统** | 风格统一、尺寸标准、命名规范 |
| **动效** | 缓动曲线、持续时间、过渡场景 |
| **文案调性** | 语气、术语、标点规范 |

规范不是一次写完的，随产品演进持续维护。

## 五、企业级产品底线（钉钉开放平台）

| 维度 | 要求 |
| --- | --- |
| **一致性** | 遵循平台设计语言，控件和交互模式统一 |
| **稳定性** | 性能基线、异常处理、容灾机制必须明确 |
| **安全性** | 数据加密、权限管控、认证机制 |
| **可发现性** | 应用图标/截图/描述必须清晰传达价值主张 |
| **文档化** | API、鉴权、安全策略必须有文档可查 |

## 六、审查清单

### UI 设计

- [ ] 是否有设计规范文档
- [ ] 色彩系统是否完整（品牌色/功能色/中性色）
- [ ] 字体层级是否成体系（字号/字重/行高）
- [ ] 间距是否遵循网格系统
- [ ] 暗色模式是否有定义
- [ ] 响应式断点是否有明确规则

### 交互/UX

- [ ] 是否“问题优先”而不是“功能堆积”
- [ ] 用户核心路径是否有断点
- [ ] 每个操作是否有状态反馈（加载/成功/失败/空）
- [ ] 错误状态是否有引导（不是只有报错）
- [ ] 表单提交是否有防重复和校验反馈

### 转化/营销

- [ ] 价值主张是否在 3 秒内传达
- [ ] CTA 是否显眼且文案有行动导向
- [ ] 信任信号是否充足（案例/数据/客户 Logo/团队）
- [ ] 联系/咨询路径是否最短

### 品牌形象

- [ ] 定位是否一以贯之（从 title 到 footer 是一个故事）
- [ ] 视觉调性是否匹配业务属性
- [ ] 团队/公司介绍是否存在
- [ ] 内容更新是否活跃（有无“死页”）

### SEO/性能

- [ ] 每个页面有独立 title/description
- [ ] 结构化数据（JSON-LD）是否完整
- [ ] 图片有 alt 且已优化
- [ ] Core Web Vitals 在合理范围

### 证据要求

- 每条问题至少附一条证据：文件:行、截图、URL、Lighthouse/axe 输出、数据。
- 没有证据的判断写入“待验证假设”，不要写成结论。
