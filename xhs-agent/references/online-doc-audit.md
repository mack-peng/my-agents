# 在线文档 vs 本地基线对比

`minitool-zip-builder` 的核心要求：**打包前必须与在线文档比对**。
本文记录实际操作数据与 fallback 策略。

## 在线文档

- 地址：<https://miniapp-sandbox.xiaohongshu.com/minitool/doc>
- 上次成功抓取时间：2026-11-06
- 实际抓到 3.09 万字符的完整能力清单（含 §2 可用能力 / §3 平台 JS API / §4 禁用能力 / §5 WebGL / §6 FAQ）

## 基线文档（冻结）

`.agents/skills/minitool-zip-builder/references/js-api.md` 是发布时的本地 API 快照，抓取于 2026-10-30。
设计意图：拿它当**比较基线**，识别在线文档相对它的新增 / 更新能力。

## 实际见效的流程（2026-11-06 实测有效）

1. **直接 `webfetch` 在线文档** → 成功，内容完整。
2. 与本地基线逐节语义比较：
   - 新增公开 API → 播报新增能力
   - 已有 API 版本/限制变化 → 播报能力更新
   - 纯文案 / 面向 AI 的编辑性调整 → 不算能力变化
3. 比较通常只需 10-20 行代码 diff，成本一次。
4. 在线文档的内容优先级**严格高于**本地基线。

## Fallback（在线文档不可达时）

- 使用本地基线 `.agents/skills/minitool-zip-builder/references/js-api.md` 保守实现
- 交付物标注「未核验在线能力」
- 提醒用户在真机验证 API 是否可用

## 关键经验

- 在线文档不使用 JS API 懒加载，`webfetch` 一次即可拿到全文。
- 不要在高频循环里每次都抓在线文档：一次任务开头抓一次就够，同会话内可复用。
- 抓到的新增能力**只有在线文档明确说可用**才算数；内部 / 预留 / 未标注开放状态的不播报。
