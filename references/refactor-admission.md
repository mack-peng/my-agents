# 重构准入清单

适用于 ticket-agent / develop-agent 及其委托的代码执行方。用户明确要求整理写法，或需求条目本身是重构时，按本清单执行；**AI 不得自动发起重构**。

> 术语：「代码分支」指 `if/else`、early return、三元、`switch`、`catch` 等条件分支，不是 git 分支。

## 1. 触发与范围

- 仅在用户明确要求或需求条目本身是重构时执行
- AI 自发发现的不整洁只列出，不动手
- 复述「写法乱」的具体所指（命名 / 结构 / 去重 / 死代码），列出非目标（不改语义、不改边界行为、不改 SSR/CSR 差异）
- 不顺手修改与重构目标无关的文件
- **分支**：不强制新开。建议新开分支；也可留在当前任务分支。两种情况都必须用独立 `refactor:` commit，禁止与 `fix:` / `feat:` 混提交

## 2. 改动前代码分支清单（动手前产出并经用户确认）

| # | 文件:行 | 条件 | 返回/行为 |
|---|---------|------|-----------|
| B1 | fe/js/components/hoc/navBarContainer.es6:33 | `!path` | `return false` |

清单必须覆盖被重构函数内的所有条件分支，包括守卫、早退、默认值、异常分支。

## 3. 意图考古

对每个将被删除或合并的分支：

```bash
git log -L <start>,<end>:<file>
git blame <file>
```

- 24 小时内新增的防御代码默认保留
- 确需删除时，必须给出「该输入不可达」的证明（调用链、payload 契约、监控证据）
- 保留的防御分支补一行注释：什么输入会命中

## 4. 改动后分支清单与映射

| # | 旧分支 | 新分支对应 | 处理（保留/合并/删除） | 证据 |
|---|--------|------------|------------------------|------|
| B1 | `!path` → false | — | 删除 | 需输入不可达证明 |

规则：

- 旧清单每条必须有映射
- 删除项必须有不可达证明并经用户确认
- 新清单不得出现清单外的新行为；出现即为行为变更，不属于纯重构

## 5. 等价性验证矩阵

| 输入场景 | 旧实现输出 | 新实现输出 | 一致 |
|----------|------------|------------|------|
| 正常路径 | | | |
| `undefined` | | | |
| `null` | | | |
| `''` | | | |
| SSR | | | |
| CSR | | | |
| 特殊页 | | | |
| 普通页 | | | |

- 无法执行差分时：逐分支推导 + 用户确认
- `No behavior change` 仅在矩阵全部一致时写入 commit body

## 6. 禁止

- 把带 early-return 的守卫压成三元表达式、`&&` 或 optional chaining
- 合并语义不同的分支（如 SSR 路径解析 vs 客户端活 UID）
- 以「看起来冗余」为由删除无注释判空
- 重构 commit 与业务修复混提交
- 无证据声明 "No behavior change"

## 7. 提交与评审

- commit 类型 `refactor:`，body 写明 Why / Before / After，并引用分支清单映射与等价矩阵结论
- MR 描述单列重构范围、删除分支证明
- 追加 commit 后重新请求 review；reviewer 必须对比 version diff 并核对旧/新分支清单
