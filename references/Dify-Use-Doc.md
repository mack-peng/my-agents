## 入门

> **阅读对象：AI Agent。目的：学习在 Dify 平台上编排工作流，将 AI 模型、工具和逻辑组合为可靠、可重复的流程。**

### 1. Dify 是什么

Dify 是一个开源 AI 工作流平台。在可视化画布上编排 AI 模型、连接数据源、定义处理流程，将领域知识转化为可运行的软件。

**核心价值**：Do It For You — 把 AI 模型的调用、数据处理、逻辑分支、输出格式化全部通过拖拽式画布完成。

**平台入口**：https://cloud.dify.ai（免费注册含 200 条消息额度，支持 OpenAI、Anthropic、Gemini 等模型）

### 2. 核心概念（AI Agent 必须理解的基础模型）

#### 2.1 应用类型

Dify 提供两种主要应用类型：

| 类型 | 说明 | 启动方式 |
|------|------|----------|
| **工作流 (Workflow)** | 处理单轮任务，适合批量执行 | 用户输入 或 触发器（定时/Webhook/插件） |
| **对话流 (Chatflow)** | 多轮对话，每轮触发一次工作流 | 仅用户输入（不能使用触发器） |

还有 3 种基础应用（底层运行相同的工作流引擎，但提供更简化的传统界面）：**聊天机器人、智能代理、文本生成器**。

**关键规则**：
- 用户输入和触发器是**互斥**的开始节点，不能同时存在
- 只有**用户输入启动**的工作流才能发布为 Web 应用、MCP 服务器或通过 API 暴露
- 对话流除了工作流功能外，还有：会话变量存储记忆、LLM 节点记忆功能、流式输出文本/图像/文件

#### 2.2 变量系统

变量是 AI Agent 编排工作流的核心，分为四类：

| 变量类型 | 说明 | 可修改 |
|----------|------|--------|
| **输入变量** | 在用户输入节点定义，由最终用户填写 | 否（运行开始时设置） |
| **输出变量** | 每个节点产生，可被后续节点引用 | 否 |
| **环境变量** | 存储 API 密钥等敏感信息，与 DSL 分离 | 否（常量） |
| **会话变量** | 仅对话流，跨多轮对话持久化 | 是（通过变量赋值器节点） |

**内置系统变量**（用户输入节点自动提供）：

| 变量名 | 类型 | 说明 |
|--------|------|------|
| `sys.user_id` | String | 用户唯一标识 |
| `sys.app_id` | String | 应用唯一标识 |
| `sys.workflow_id` | String | 工作流 ID |
| `sys.workflow_run_id` | String | 运行 ID，用于追踪日志 |
| `sys.timestamp` | Number | 每次执行开始时间 |

**变量引用方式**：
- 下拉菜单选择：配置输入字段时直接选择
- 斜杠输入：在文本框中键入 `/` 从下拉菜单选择变量

#### 2.3 DSL 导出

所有 Dify 应用可导出为 YAML 格式的领域特定语言 (DSL) 文件，也可以从 DSL 文件创建应用，方便移植和分享。

### 3. 30分钟快速入门实战：多平台内容生成器

> 通过一个完整工作流案例，掌握 Dify 核心节点的编排方法。
> 最终产物：输入任意内容（文本/文档/图片）+ 语调和语言 → 生成针对各社交平台定制的帖子。

#### 前置准备

1. 注册 https://cloud.dify.ai（Sandbox 计划含 200 条免费消息额度）
2. 设置 > 模型供应商 > 安装 OpenAI 插件（本教程用 gpt-5.2）
3. 系统模型设置 > 将系统推理模型设为 gpt-5.2

#### 创建应用

工作室 > 从空白创建 > 工作流 > 命名"多平台内容生成器"

#### 步骤 1：用户输入节点 — 定义收集的输入

添加**用户输入节点**，配置以下输入字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `draft` | 文本 | 草稿内容 |
| `user_file` | 文件 | 参考材料（图片/文档） |
| `voice_and_tone` | 文本 | 语音和语调 |
| `platform` | 文本 | 目标平台（支持自由文本，≤10个） |
| `language` | 文本 | 语言要求 |

> **关键认知**：用户输入节点中定义的每个字段，都会自动成为所有下游节点可引用的变量。

#### 步骤 2：参数提取器节点 — 结构化自由文本

用户输入的平台字段是自由文本（如"x 和 linkedIn"），需转换为标准数组 `["Twitter", "LinkedIn"]`。

添加**参数提取器节点**，配置：
- 输入变量：`User Input/platform`
- 提取参数：名称 `platform`，类型 `Array[String]`，必填
- 指令（Prompt）：

```
# TASK DESCRIPTION
Parse platform names from input and output as a JSON array.

## PROCESSING RULES
- Support multiple delimiters: commas, semicolons, spaces, line breaks, "and", "&", "|", etc.
- Standardize common platform name variants (twitter/X→Twitter, insta→Instagram, etc.)
- Remove duplicates and invalid entries
- Preserve unknown but reasonable platform names
- Preserve the original language of platform names

## OUTPUT REQUIREMENTS
- Success: ["Platform1", "Platform2"]
- No platforms found: [No platforms identified. Please enter a valid platform name.]
```

> **技巧**：错误消息 "No platforms identified..." 是故意设计的，作为下一步 IF/ELSE 的触发条件。

#### 步骤 3：IF/ELSE 节点 — 验证与分流

添加**IF/ELSE 节点**，检查平台提取：
- IF 条件：`Parameter Extractor/platform` 包含 `No platforms identified. Please enter a valid platform name.`
- **IF 分支** → 添加**输出节点**，设置输出变量为 `Parameter Extractor/platform`（返回错误消息）
- **ELSE 分支** → 继续正常流程

> **模式**：提前验证输入 → 无效则提前终止 → 节省后续 LLM 调用开销。

#### 步骤 4：列表操作器节点 — 按类型分流文件

用户可上传图片和文档，需分开处理（图片直接给 GPT 视觉能力，文档需先转文本）。

在 ELSE 分支后添加**两个并行的列表操作器节点**：

**图像节点**：
- 输入变量：`User Input/user_file`
- 过滤条件：`{x}type 在 Image`

**文档节点**：
- 输入变量：`User Input/user_file`
- 过滤条件：`{x}type 在 Doc`

#### 步骤 5：文档提取器节点 — 将文档转文本

GPT 不能直接读取 PDF/DOCX，需先转换。

在文档节点后添加**文档提取器节点**：
- 输入变量：`Document/result`

#### 步骤 6：LLM 节点 — 整合所有参考材料

将草稿文本、文档文本、图像整合为统一摘要，供后续内容生成使用。

添加**LLM 节点**，命名为"整合信息"：
- **同时连接**：文档提取器节点 + 图像节点
- 启用 **VISION**，视觉变量设为 `Image/result`
- 系统指令：

```
# ROLE & TASK
You are a content strategist. Analyze the provided draft and reference materials (if any), then create a comprehensive content foundation for multi-platform social media optimization.

# ANALYSIS PRINCIPLES
- Work exclusively with provided information—no external assumptions
- Focus on extraction, synthesis, and strategic interpretation
- Identify compelling and actionable elements
- Prepare insights adaptable across different platforms

# REQUIRED ANALYSIS
Deliver structured analysis with:

## 1. CORE MESSAGE
- Central theme, purpose, objective
- Key value or benefit being communicated

## 2. ESSENTIAL CONTENT ELEMENTS
- Primary topics, facts, statistics, data points
- Notable quotes, testimonials, key statements
- Features, benefits, characteristics mentioned
- Dates, locations, contextual details

## 3. STRATEGIC INSIGHTS
- What makes content compelling/unique
- Emotional/rational appeals present
- Credibility factors, proof points
- Competitive advantages highlighted

## 4. ENGAGEMENT OPPORTUNITIES
- Discussion points, questions emerging
- Calls-to-action, next steps suggested
- Interactive/participation opportunities
- Trending themes touched upon

## 5. PLATFORM OPTIMIZATION FOUNDATION
- High-impact: Quick, shareable formats
- Professional: Business-focused discussions
- Community: Interaction and sharing
- Visual: Enhanced with strong visuals

## 6. SUPPORTING DETAILS
- Metrics, numbers, quantifiable results
- Direct quotes, testimonials
- Technical details, specifications
- Background context available
```

- 用户消息：

```
Draft: {{User Input/draft}}
Reference material: {{Doc Extractor/text}}
```

#### 步骤 7：迭代节点 — 为每个平台生成定制内容

**迭代节点**循环遍历平台列表，为每个平台运行子工作流。

在"整合信息"节点后添加**迭代节点**：
- 输入变量：`Parameter Extractor/platform`
- 输出变量：`Create Content/structured_output`
- **启用并行模式**，最大并行度：10

> **为什么用迭代而不是并行分支？**因为平台数量不固定（用户可能输入 1-10 个）。

**迭代节点内部的子工作流：**

**子节点 1 — LLM「识别风格」**：分析平台特性，给出内容指南

```
# ROLE & TASK
You are a social media expert. Analyze the platform and provide content creation guidelines.

# ANALYSIS REQUIRED
For the given platform, provide:

## 1. PLATFORM PROFILE
- Platform type and category
- Target audience characteristics

## 2. CONTENT GUIDELINES
- Optimal content length (characters/words)
- Recommended tone (professional/casual/conversational)
- Formatting best practices (line breaks, emojis, etc.)

## 3. ENGAGEMENT STRATEGY
- Hashtag recommendations (quantity and style)
- Call-to-action best practices
- Algorithm optimization tips
```

### 4. 入门阶段核心收获

1. **工作流 = 节点 + 连线**：每个节点有明确职责，数据通过变量在节点间流动
2. **变量是灵魂**：用户输入 → 节点输出 → 下游引用，形成数据流
3. **节点选择原则**：
   - 能用确定性节点就不要用 LLM（如模板格式化 vs LLM 格式化）
   - 提前验证输入，无效则尽早终止（IF/ELSE + 输出节点）
   - 结构化输出 > 自由文本输出（可靠性）
4. **迭代节点是核心**：处理数量不定的列表数据
5. **Prompt 工程**：每个 LLM 节点的系统指令定义角色、任务、输出格式，用户消息传递具体数据
6. **并行 vs 迭代**：知道并行数量用并行分支，不知道则用迭代节点

## 构建

> **阅读对象：AI Agent。目的：掌握 Dify 工作流编排的全部节点和技巧，能够构建生产级 AI 工作流。**

### 工作流与对话流

#### 概述：为什么需要 Agentic 工作流

AI 模型单独使用不够可预测（幻觉、遗漏步骤、输出不一致）。**Agentic 工作流**将 AI 能力嵌入结构化、可重复的流程——设计流程来逐步编排模型、工具和逻辑，包含明确的条件、检查点和回退路径。AI 在定义的边界内运行。

#### 工作流 vs 对话流

两者共享可视化画布和节点系统。核心区别在于**用户交互方式**：

| 维度 | 工作流 | 对话流 |
|------|--------|--------|
| 运行模式 | 从头到尾运行一次 | 每轮对话触发一次 |
| 起始节点 | 用户输入 **或** 触发器 | 仅用户输入 |
| 结束节点 | 输出（可选） | 直接回复（必需） |
| 适用场景 | 报告生成、数据管道、批处理 | 交互助手、引导问答 |
| 额外能力 | — | 内容审核、文字转语音 |

**触发器**支持：定时、Webhook、插件事件。对话流始终由用户消息启动，无触发器。

**编排方式**：拖拽 > 连接 > 配置。大部分工作无需编码，仅在现有节点不满足时写代码。

#### 编排逻辑

构建工作流时，节点按**串行**或**并行**排列：

| 方式 | 行为 | 变量访问 |
|------|------|----------|
| 串行 | 节点依次运行 | 可读取链中任何前序节点的变量 |
| 并行 | 节点同时运行 | 彼此无法读取变量；汇合后下游节点可读取所有分支变量 |

**限制**：单条路径最多 50 个节点（自托管可通过 `MAX_TREE_DEPTH` 调整）。

**节点复用**：
- 除用户输入节点外，所有节点可复制粘贴（同工作流内、跨工作流、跨 Dify 实例）
- 跨实例粘贴需 HTTPS 加载或通过环回地址访问
- 节点配置迁移时会重新评估：工作流资源（变量）、工作区资源（工具、插件、知识库）

**迭代与循环**：若节点需多次运行（按列表每项一次，或直到满足条件），将其置于**迭代**或**循环**节点内部。

#### 节点

##### 用户输入节点

收集用户输入以启动工作流和对话流应用程序。只能有一个用户输入节点。

**输入变量**：

| 类别 | 变量名 | 说明 |
|------|--------|------|
| 预设 | `userinput.files` | 用户运行时上传的文件（工作流中视为遗留，推荐自定义文件字段） |
| 预设 | `userinput.query` | 仅对话流：自动捕获用户最新消息 |
| 自定义 | — | 配置自定义输入字段，每个字段成为下游可引用变量 |

**自定义输入类型**：
- 文本输入：短文本（≤256字符）、段落
- 结构化输入：选择（下拉菜单）、数字、复选框、JSON 代码
- 文件输入：单个文件、文件列表

**文件处理注意**：用户输入节点只收集文件（元数据：名称/大小/类型），不解析内容。文件需由后续节点处理：
- 文档 → 文档提取器节点（转文本）
- 图像 → 有视觉能力的 LLM 节点
- CSV/JSON → 代码节点
- 混合文件 → 列表操作符节点按类型分离再分流

**隐藏并预填**：
- 适用场景：已知值无需用户填写（如产品标识符、租户 ID）
- 操作：取消勾选必填 → 勾选隐藏并预填 → 发布后通过 URL 参数传递
- 注意：隐藏字段值会出现在 URL 查询字符串中，**不保密**。凭据/API 密钥改用**环境变量**
- 不支持：文件类型字段

**URL 预填模式**：
```
{WEBAPP_URL}?{VARIABLE_NAME}={VALUE}&{VARIABLE_NAME}={VALUE}
示例：https://udify.app/chat/abc123?productName=Acme&region=us-east
```

##### 触发器 - 概述

触发器仅适用于**工作流**应用（对话流无触发器）。

**能力**：使工作流定时运行或当外部系统事件发生时自动运行（无需用户交互或 API 调用）。

**多触发器**：一个工作流可拥有多个并行的触发器，可在同一画布上构建多个以不同触发器为起点的独立工作流。

**配额限制**（Cloud Sandbox）：每个工作流最多 2 个触发器。触发事件受套餐配额限制。

**触发器类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| 定时触发器 | 指定时间点自动运行 | 每天 9 点生成销售报告（最多 1 个） |
| 插件触发器 | 通过插件订阅外部事件 | Slack 新消息触发分析归档 |
| Webhook 触发器 | 通过自定义 webhook 订阅事件 | 电商新订单自动处理 |

**选择思路**：
- 目标系统有可用触发器插件 → 用**插件触发器**
- 无合适插件或需订阅插件不支持的事件 → 用 **Webhook 触发器**

**启用/禁用**：在快捷设置中可启用/禁用已发布的触发器。被禁用的触发器不会触发工作流。

**测试多个触发器**：点击 测试运行 > 运行所有触发器。第一个运行的触发器将启动工作流，其余被忽略。点击后：定时触发器在下一计划时间运行；插件触发器开始监听事件；Webhook 触发器开始监听 HTTP 请求。

##### 定时触发器

每个工作流最多只能有一个定时触发器。用于执行周期性重复任务（如每日报告、定时通知）。

**配置方式**：
1. 可视化配置：简单时度/日度/周度/月度计划。周度或月度可同时选多天。
2. Cron 表达式：更复杂精确的计划（可借助 LLM 生成）。

配置后可见接下来 5 次计划运行时间。定时触发器不产生输出变量，但触发时更新系统变量 `sys.timestamp`。

**Cron 格式**：`分钟 小时 日 月 星期几`（5个字段，空格分隔）

| 特殊字符 | 含义 | 示例 |
|---------|------|------|
| `*` | 每个 | `*` 小时 = 每小时 |
| `,` | 分隔多个值 | `1,3,5` 星期几 = 周一三五 |
| `-` | 范围 | `9-17` 小时 = 9-17点 |
| `/` | 步进 | `*/15` 分钟 = 每15分钟 |
| `L` | 最后 | `L` 日 = 月末；`5L` 星期几 = 最后周五 |
| `?` | 任意/忽略 | 与 `*` 类似但更精确 |

**预定义表达式**：`@yearly`、`@monthly`、`@weekly`、`@daily`、`@hourly`

**示例**：
| 时间 | Cron |
|------|------|
| 工作日上午9点 | `0 9 * * MON-FRI` |
| 每周三14:30 | `30 14 * * WED` |
| 每月最后一天17点 | `0 17 L * *` |
| 每月最后一个周五22点 | `0 22 * * 5L` |

**测试**：运行此步骤 → 忽略计划立即运行。测试运行 → 等待下一计划时间。

##### 插件触发器

通过触发器插件订阅外部系统事件（如 GitHub PR、Push、Issue），事件发生时自动运行工作流。

**添加方式**：右键 > 添加节点 > 开始 > 选择可用插件触发器，或在 Dify 插件市场搜索。

**订阅**：每个插件最多 10 个订阅/工作区。每个订阅基于一个 webhook。

**创建订阅方式**：

| 方式 | 说明 | 适用场景 |
|------|------|----------|
| OAuth 自动创建 | Dify 代表你在外部系统创建 webhook | Cloud 有预配置 OAuth 客户端；自托管需自定义 OAuth |
| API Key 自动创建 | 通过 API key 授权 | 插件支持时 |
| 手动创建 | 使用 Dify 回调 URL 自行创建 webhook | 无需授权 |

**建议**：创建订阅时选择所有可用事件，后续添加的任何插件触发器均可复用同一订阅。

**变量**：插件触发器的输出变量由其插件定义，不可修改。

**多分支共享**：多个插件触发器分支共享下游节点时，用**变量聚合器**汇聚，避免重复配置。

**测试**：未发布的插件触发器须先点击 运行此步骤 或测试运行整个工作流，使触发器进入监听状态，否则不会捕获事件。

##### Webhook 触发器

通过自定义 webhook URL 监听外部 HTTP 请求，事件发生时自动运行工作流。

**工作原理**：添加 Webhook 触发器 → 系统生成 webhook URL → 在外部系统用此 URL 创建 webhook → 外部系统发 HTTP 请求到 URL → 工作流触发 → 提取的事件数据成为下游变量。

**配置项**：
- **HTTP 方法**：必须与外部系统发送请求的方法一致，否则请求被拒绝
- **内容类型**：必须与外部请求的 Content-Type 一致，否则被拒绝
- **参数提取**：从查询参数、请求头、请求体中提取特定参数，成为输出变量
- **响应**：默认 200 OK，可自定义状态码（200-399）和响应体（JSON/纯文本）

**参数设置**：
| 字段 | 说明 |
|------|------|
| 变量名 | 请求参数中的键名（请求头中的连字符自动转下划线） |
| 类型 | 预期数据格式（仅查询/请求体参数，请求头固定为字符串） |
| 必填 | 是否必需；缺少必填参数则工作流不触发 |

**测试专用 URL**：始终使用测试专用的 webhook URL 分离测试与生产数据。

**测试流程**：
1. 使用测试专用 URL 在外部系统创建 webhook
2. 设置正确的 HTTP 方法和内容类型
3. 点击 运行此步骤 使触发器开始监听
4. 在外部系统手动触发事件
5. 在触发器 上次运行 日志的 输入 中查看接收到的请求数据

**错误响应**（不可自定义）：400、404、413、500

**响应体转换**：非 JSON 内容自动转 JSON（如 `OK` → `{"message": "OK"}`）

##### 大语言模型节点

调用 LLM 处理文本、图像和文档。发送提示词并捕获响应，支持结构化输出、上下文管理和多模态输入。

**前置条件**：在系统设置 → 模型供应商中配置至少一个模型。

**模型参数**：

| 参数 | 说明 |
|------|------|
| 温度 (0-1) | 0=确定性，1=创造性 |
| 核采样 | 通过概率限制词汇选择 |
| 频率惩罚 | 减少重复 |
| 存在惩罚 | 鼓励新话题 |
| 预设 | 精确、平衡、创意 |

**提示词配置**：
- 聊天模型：消息角色（系统/用户/助手）
- 完成模型：简单文本续写
- 变量引用：双花括号 `{{variable_name}}`

**上下文变量**：连接知识检索节点输出到 LLM 节点上下文输入，实现 RAG。Dify 自动追踪引用来源。

**结构化输出**：强制模型返回特定格式（如 JSON）。三种配置方法：
1. 可视化编辑器（添加字段、类型、描述，自动生成 JSON Schema）
2. JSON Schema（手动编写）
3. AI 生成

**注意**：原生 JSON 支持的模型可可靠处理；其他模型由 Dify 在提示词中包含 Schema，结果可能有差异。

**记忆**：仅对话流。在多次 LLM 调用间维护上下文。节点特定，不跨对话持久化。通过编辑 USER 模板自定义提示词。

**视觉能力**：
- 默认变量：`userinput.files`（自动从用户输入节点获取）
- 细节控制：高细节（准确但消耗更多 token）/ 低细节（快速处理）
- 模型支持：GPT-4V 处理图像，Claude 直接处理 PDF

**Jinja2 模板支持**：支持循环、条件、复杂数据转换：
```jinja2
{% for item in search_results %}
{{ loop.index }}. {{ item.title }}: {{ item.content }}
{% endfor %}
```

**流式输出**：默认支持。每个文本块作为 RunStreamChunkEvent 产生，实现实时响应。文件输出在流式传输时自动处理。

**错误处理**：
- 重试：最大重试次数、重试间隔、退避乘数
- 回退策略：默认值、错误路由、替代模型

##### 知识检索节点

将已有知识库集成到工作流/对话流中。检索与查询相关的信息，输出结果供下游 LLM 使用。

**前置条件**：至少有一个可用知识库。

**配置三要素**：
1. 检索什么（查询内容）
2. 在哪里检索（知识库）
3. 如何处理结果（节点级检索设置）

**查询内容**：
- 查询文本：选择文本变量（Chatflow 用 `userinput.query`，Workflow 用文本类型变量）
- 查询图片：选择图片变量（≤2MB，需添加多模态知识库才会出现该选项）

**知识库选择**：可添加多个，同时检索并合并结果。Vision 图标表示支持跨模态检索。

**节点级检索设置**：

| 设置 | 说明 |
|------|------|
| 权重设置 | 语义 vs 关键词匹配权重（仅所有知识库为高质量索引时可用） |
| Rerank 模型 | 对结果重新评定排序。多模态知识库需选多模态 Rerank 模型 |
| Top K | 重排序后返回的最大结果数 |
| Score 阈值 | 最低相似度分数，低于此值过滤 |

**元数据过滤**：将检索范围限定在符合指定元数据条件的文档内，适用于内容多样的大型知识库。

**输出变量**：`result` — 包含分段内容、元数据、标题等属性的文档分段数组。含图片时有 `files` 字段。

**搭配 LLM 使用**：
1. 在 LLM 节点的 上下文 字段选择 `result` 变量
2. 提示词中引用 上下文 变量 + 用户输入变量
3. 可选：启用 Vision 让 LLM 理解检索到的图片（无需再手动引用上下文）

##### 直接回复节点

仅适用于**对话流**应用（工作流对应的是输出节点）。定义向用户传递的内容。

**能力**：格式化响应、将文本与变量结合、流式传输多模态内容（文本+图像+文件）。

**内容配置**：
- 使用 `{{variable_name}}` 语法引用任何前序节点变量
- 支持固定文本、变量插入、Markdown 格式化

**多模态响应**：
- 文本：变量替换 + Markdown + 动态内容
- 图像：工具生成的、用户上传的或节点处理的图像，与文本一起流式传输
- 文件：工作流执行期间生成或处理的文档/电子表格

**多个直接回复节点**：可在不同位置放置多个，实现：
- 渐进式响应：后台处理继续，同时提供即时确认
- 条件响应：基于分支逻辑发送不同内容
- 流式更新：部分结果一旦可用立即传递

**变量集成**：无缝集成所有节点类型的输出——LLM 响应、知识检索、工具结果、文件处理等。变量系统维护类型安全，自动处理不同内容类型。

##### 输出节点

仅适用于**工作流**应用（对话流用直接回复节点）。将工作流特定变量值返回给终端用户或 API 调用者。

**可选**（前身是必需的结束节点）：没有输出节点的工作流仍可运行，但不返回数据。

**配置输出变量**：
- 每个输出节点至少一个变量，指定名称和数据来源
- 变量名称成为 API 响应中的键名
- 单个节点可添加多个变量，拖拽调整顺序

**支持的变量类型**：string、number、integer、boolean、object、file、array[string/number/object/boolean/file]

**多个输出节点**：
- 不终止工作流，并行分支继续运行
- 所有已执行输出节点的变量合并为一个最终结果
- 同一分支按排列顺序添加；并行分支按完成顺序添加
- 变量名称**不可重复**，后执行的会覆盖先前的值

**API 响应结构**（阻塞式返回）：
```json
{
  "workflow_run_id": "...",
  "status": "succeeded",
  "outputs": {
    "result_text": "The processed output...",
    "score": 95
  }
}
```

**发布为工具**：输出节点定义工具的返回结构，变量名成为工具结果中的键。

##### 智能代理节点

让 LLM 自主控制工具，动态推理问题，迭代决定使用哪些工具以及何时使用。

**智能代理策略**：
- **函数调用**：使用 LLM 原生函数调用能力，适合 GPT-4、Claude 3.5 等
- **ReAct（推理与行动）**：逐步推理 + 行动
- 可从应用市场安装其他策略

**配置**：
- **模型**：支持所选策略的 LLM（函数调用策略需模型支持函数调用）
- **工具**：授权（API 密钥）、描述（何时使用）、参数（必需/可选）
- **指令/上下文**：自然语言定义角色和目标，使用 Jinja2 引用上游变量

**执行控制**：
- 最大迭代次数（简单 3-5，复杂 10-15）
- 记忆：TokenBufferMemory（更多上下文但增加 token 成本）

**工具参数自动生成**：`auto: false` 的参数由智能代理自动填充；手动输入参数需明确值。

**输出变量**：
| 变量 | 说明 |
|------|------|
| 最终答案 | 智能代理最终响应 |
| 工具输出 | 每次工具调用结果 |
| 推理轨迹 | 逐步决策过程（ReAct 特别详细） |
| 迭代计数 | 推理循环次数 |
| 成功状态 | 是否成功完成任务 |
| 智能代理日志 | 结构化日志事件，用于调试 |

**最佳实践**：
- 清晰的工具描述帮助代理决策
- 适当的迭代限制防止失控成本
- 详细的指令提供角色和目标上下文
- 记忆管理平衡上下文保留与 token 效率

##### 代码节点

执行自定义 Python 或 JavaScript 代码处理数据转换、计算和复杂逻辑。当预设节点不满足需求时使用。

**配置**：定义输入变量（引用上游节点数据），函数必须返回包含输出变量的字典：
```python
def main(input_variable: str) -> dict:
    result = input_variable.upper()
    return {'output_variable': result}
```

**语言支持**：
- Python：标准库（json, math, datetime, re）+ 外部依赖（numpy, pandas, requests）
- JavaScript：lodash, moment 等
- 均在安全沙箱中运行

**错误处理**：
- 重试：最多 10 次，间隔最大 5000ms
- 回退：代码失败时定义后续路径

**输出验证限制**：
| 类型 | 限制 |
|------|------|
| 字符串 | 最大 80,000 字符，空字节移除 |
| 数字 | -999999999 ~ 999999999，浮点数 10 位小数 |
| 对象/数组 | 最大深度 5 级 |

**安全**：沙箱执行，阻止文件系统访问、网络请求和系统命令。Cloudflare WAF 可能阻止危险操作。

**自托管**：需启动沙箱服务：
```
docker-compose -f docker-compose.middleware.yaml up -d
```

**常见用例**：数据解析、数学运算、数据转换、条件逻辑

##### 问题分类器节点

基于 LLM 语义理解对用户输入进行分类，将对话路由到不同分支路径。无需手动构建复杂条件。

**输入和模型设置**：
- 输入变量：选择要分类的内容（通常用 `sys.query`）
- 模型选择：简单分类用快速模型，边界细微时用更强模型

**分类定义**（每个分类包含两段独立文本）：
| 要素 | 说明 | 下游输出变量 |
|------|------|-------------|
| 分类描述（编辑器正文） | 模型选择分支时读取的内容，用边界表述帮助判断 | 通过 `class_name` 输出 |
| 分类标题（小标题） | 画布上的标签，可双击重命名 | 通过 `class_label` 输出 |

每个分类对应一条输出路径，可连接不同下游节点。

**示例**（客服场景）：
| 用户输入 | 分类结果 |
|---------|---------|
| 如何在 iPhone 14 上设置联系人？ | 产品使用 |
| 保修期是多长？ | 售后服务 |
| 今天天气如何？ | 其他问题 |

**高级配置**：在 指令 字段中添加详细分类指南，处理边界场景、模棱两可的情况或特定业务规则。

##### If-Else 节点

通过条件判断将工作流路由到不同分支路径。

**分支逻辑**：
| 分支 | 说明 |
|------|------|
| IF | 主要条件为真时执行 |
| ELIF | IF 为假时按顺序检查（可添加多个） |
| ELSE | 无匹配时的后备选项 |

**条件类型**：
| 类别 | 运算符 |
|------|--------|
| 文本操作 | 包含/不包含、开头为/结尾为、是/不是 |
| 值检查 | 等于、不等于、大于、小于、大于等于、小于等于、为空/不为空 |

**复杂条件**：使用 AND（所有条件为真）和 OR（任一条件为真）组合多个条件。

**变量引用**：引用上游节点的输出。使用变量选择器或 `{{variable_name}}` 语法。

##### 人工介入节点

在关键点暂停工作流，发送可自定义的请求表单供人工审核、提供输入或决策。

**发送方式**：
| 渠道 | 说明 |
|------|------|
| WebApp | 向 WebApp 终端用户显示表单（触发器启动的工作流不可用）。外部客户端可通过 Service API 获取 |
| 邮件 | 发送链接至工作区成员、外部邮箱或全体成员。无需 Dify 账户 |

请求在收到第一个响应后关闭。

**表单内容**：
- Markdown 格式化（标题、列表、链接等）
- 变量引用显示动态数据
- 推理模型：默认显示思维过程+答案。如需仅显示答案，开启 LLM 节点的**思维链分离渲染**
- 输入字段：可空/预填变量或静态文本，接收人可编辑。每个字段成为下游变量
- 特殊变量：`__rendered_content` — 填入所有值的完整表单内容

**用户动作**：定义决策按钮，每个按钮路由到不同分支。按钮属性：
- `__action_id` — 按钮 ID
- `__action_value` — 按钮标题（文本）

**超时策略**：默认 3 天。超时后沿超时分支继续（如无连接则工作流结束）。

##### 迭代节点

对数组的每个元素按顺序或并行运行相同的工作流步骤，用于批处理任务。

**核心组件**：
| 组件 | 说明 |
|------|------|
| 输入变量 | 上游节点的数组数据 |
| 内部工作流 | 对每个元素执行的处理步骤 |
| 输出变量 | 所有迭代收集的结果（也是数组） |

**内置变量**：
- `items[object]` — 当前处理的数组元素
- `index[number]` — 当前迭代索引（从 0 开始）

**处理模式**：
| 模式 | 说明 |
|------|------|
| 顺序 | 逐条处理，支持流式结果返回，内存占用低，顺序可预测 |
| 并行 | 独立操作时追求速度 |

**错误处理策略**：
| 策略 | 说明 |
|------|------|
| 终止 | 出现错误时停止处理 |
| 错误时继续 | 跳过失败，输出 `null`（输入 [1,2,3] → 输出 [result-1, null, result-3]） |
| 移除失败结果 | 跳过失败，只返回成功结果（输入 [1,2,3] → 输出 [result-1, result-3]） |

**输出处理**：迭代输出数组，需转换后使用。用代码节点或模板节点将数组转为文本。

**最佳实践**：选择适当的模式、优雅处理错误、优化内部工作流、监控资源使用。

##### 循环节点

执行重复性工作流，每个循环基于前一个循环的结果进行构建，用于渐进式改进。

**循环 vs 迭代**：
| 特性 | 循环 | 迭代 |
|------|------|------|
| 处理方式 | 顺序，每个循环依赖前一个结果 | 独立处理数组元素 |
| 状态管理 | 变量在循环中持续存在并累积 | 无状态 |
| 使用场景 | 内容优化、问题解决、质量保证 | 批处理、数组处理 |

**循环变量**：在迭代中持续存在，循环完成后仍可访问。

**终止条件**：
| 方式 | 说明 |
|------|------|
| 循环终止条件 | 表达式判断（如 `quality_score > 0.9`） |
| 最大循环次数 | 防止无限循环的安全限制 |
| 退出循环节点 | 达到此节点时立即终止 |

未指定条件时，循环会持续到达到最大次数。

**示例**：内容优化工作流——通过多次 LLM 审查逐步改进文本，每次迭代引用前一轮的输出，在质量达标时通过条件判断退出循环。

**最佳实践**：定义明确的退出条件、设置合理限制、有效管理状态、监控进度。

##### 模板转换节点

使用 Jinja2 模板语法将多个来源的数据转换和格式化为结构化文本。

**变量替换**：`{{ variable_name }}`，支持点号和括号语法：`{{ user.name }}`、`{{ items[0].title }}`

**条件逻辑**：
```jinja2
{% if user.subscription == 'premium' %}
  欢迎回来
{% else %}
  考虑升级
{% endif %}
```

**循环迭代**：
```jinja2
{% for item in search_results %}
### {{ loop.index }}. {{ item.title }}
---
{% endfor %}
```

**过滤器**：`{{ name | upper }}`、`{{ price | round(2) }}`、`{{ tags | join(', ') }}`、`{{ score | default('N/A') }}`

**错误处理**：使用 `default()` 过滤器和条件检查处理缺失数据。

**交互式表单**（仅 Chatflow）：可在对话中生成 HTML 表单收集结构化数据。`<form data-format="json">` 提交为 JSON，否则为纯文本。支持 input/textare/select/checkbox/button。

**快速回复按钮**（表单外独立 `<button>`）：
| 属性 | 行为 |
|------|------|
| `data-message` | 将文本作为用户消息发送 |
| `data-link` | 在新标签页打开 URL（优先于 data-message） |

**输出限制**：400,000 字符（可通过 `TEMPLATE_TRANSFORM_MAX_LENGTH` 配置）。

##### 变量聚合器节点

将互斥工作流分支汇聚为单一输出，消除重复的下游配置。

**适用场景**：条件分支、问题分类器等创建的互斥分支（每次仅一条执行）。

**注意**：不合并并行分支的输出（并行合并请用代码节点或模板转换）。

**配置**：
- 从每条分支添加需相同下游处理的变量
- 所有变量必须**相同数据类型**（string、number、object、boolean、array、file）
- 运行时输出有值的变量（仅一条分支有值）

**聚合分组**：当有多组变量需分别汇聚时，启用聚合分组创建独立分组。

##### 文档提取器节点

将上传的文档转换为 LLM 可处理的文本。文件上传和 AI 分析之间的桥梁。

**支持的文件类型**：
| 类别 | 格式 |
|------|------|
| 文本文档 | TXT, Markdown, HTML |
| 办公文档 | DOCX（直接解析）, DOC（需 Unstructured API） |
| PDF | 基于文本的 PDF（pypdfium2 提取） |
| 电子表格 | XLS/XLSXX/CSV（转换为 Markdown 表格） |
| 演示文稿 | PPT/PPTX（需 Unstructured API） |
| 邮件 | EML, MSG |
| 其他 | EPUB, VTT, JSON/YAML, Properties |

**输入/输出**：
- 单文件 → string
- 多文件数组 → array[string]
- 输出变量名：`text`

**编码处理**：chardet 自动检测，UTF-8 后备。表格转为 Markdown 格式。

**外部依赖**：旧版 DOC、PPT、EPUB 等需配置 `UNSTRUCTURED_API_URL` 和 `UNSTRUCTURED_API_KEY`。

##### 变量赋值器节点

管理对话流应用中的持久化会话变量。会话变量在整个聊天会话期间持续存在（vs 工作流变量每次执行重置）。

**配置要素**：
- 变量：选择要写入的会话变量
- 设置变量：从上游节点选择源数据
- 操作模式：覆写、追加、清除等

**操作模式（按类型）**：
| 类型 | 操作 |
|------|------|
| string | 覆写、清除、设置固定值 |
| number | 覆写、清除、设置 |
| boolean | 覆写、清除、设置 |
| object | 覆写、清除、设置 |
| array | 覆写、追加、清除 |

**常见模式**：
- 智能记忆系统：分析输入，提取事实存储到数组中
- 用户偏好存储：捕获初始偏好并在后续响应中引用
- 渐进式清单：跨对话轮次跟踪完成状态

##### 参数提取器节点

使用 LLM 将非结构化文本转换为结构化数据。弥合自然语言与结构化参数间的差距。

**输入和模型**：选择包含待提取文本的变量。选择结构化输出能力强的模型。

**参数定义**：
- 参数名称（JSON 键名）
- 数据类型（string、number、boolean、array、object）
- 描述（帮助 LLM 理解提取内容）
- 必需状态
- 支持从现有工具快速导入

**提取指令**：编写清晰指令，提供示例以提高准确性。

**推理模式**：
| 模式 | 说明 |
|------|------|
| 函数调用/工具调用 | 模型结构化输出，强类型合规 |
| 基于提示词 | 纯提示词技术，适合不支持函数调用的模型 |

**记忆**：启用后包含对话历史，提高交互式对话中的提取准确性。

**输出变量**：
- 提取的参数作为与定义匹配的变量
- 内置变量：`__is_success`（1 成功/0 失败）、`__reason`（失败描述）

**常见用例**：工具参数准备、数据格式转换、表单数据处理、API 参数构建。

**最佳实践**：清晰的参数描述、指令中提供示例、使用适当数据类型、检查 `__is_success` 处理提取失败。

##### HTTP 请求节点

连接工作流到外部 API 和 Web 服务。

**HTTP 方法**：GET、POST、PUT、PATCH、DELETE、HEAD

**核心配置**：
- URL：支持变量替换 `{{variable_name}}`，深度对象访问如 `{{api_response.data.items[0].id}}`
- 超时：连接超时、读取超时、写入超时
- 身份验证：无认证、API Key（Basic/Bearer/自定义）
- 请求正文：JSON、表单数据、二进制、原始文本

**文件检测**：自动判断文件响应——Content-Disposition 分析、MIME 评估、内容采样（前 1024 字节）。文本响应为常规数据，二进制为文件变量。

**文件操作**：
- 上传：使用二进制请求正文，从先前节点选择文件变量
- 下载：响应含文件时自动处理，可作为文件变量供下游使用

**错误处理**：
- 重试：最多 10 次，间隔最大 5000ms
- 回退：请求失败时定义替代工作流路径

**响应处理**（下游可分别访问）：
| 变量 | 说明 |
|------|------|
| 响应正文 | API 返回的主要内容 |
| 状态码 | HTTP 状态码 |
| 头部 | 键值对响应元数据 |
| 文件 | API 返回的文件内容 |
| 大小信息 | 内容字节数及可读格式（KB/MB） |

**SSL 验证**：每个节点可配置 `ssl_verify`，支持自签名证书。

##### 列表操作符节点

筛选、排序和选择数组中的元素。处理混合文件上传或需要分离组织的数据集。

支持的输入类型：`array[string]`、`array[number]`、`array[file]`、`array[boolean]`

**操作**：
- 筛选：按类型、MIME 类型、扩展名提取项目
- 排序：升序（ASC）或降序（DESC）
- 选择：取前 N 个、第一条记录、最后一条记录

**输出变量**：
| 变量 | 说明 |
|------|------|
| result | 完整筛选+排序数组，用于批量处理 |
| first_record | 第一个匹配元素的单个值 |
| last_record | 最后一个匹配元素的单个值 |

**混合文件处理示例**：用户同时上传文档+图像→列表操作符按类型分离→图像路由到多模态 LLM、文档路由到提取器→合并结果。

##### 工具节点

将 Dify 工具作为独立节点加入工作流，与外部服务和 API 交互（网页搜索、数据库查询、内容处理等）。

**添加方式**：画布上点击 添加节点 > 工具，选择操作。

**认证**：选择已有凭证或创建新凭证。可在 工具/插件 页面管理默认凭证。

## 调试

##### 单节点测试

单独测试任何节点而无需运行整个工作流。选择节点→提供测试输入→点击运行查看输出。

注意：答案节点和结束节点不支持单节点测试。

**逐步执行**：一次运行一个节点，输出缓存在变量检查器中。可编辑缓存的变量测试不同场景，无需重新运行上游节点。

**查看执行历史**：节点上的「上次运行」查看最近执行的输入、输出和耗时。

##### 变量检查器

显示所有流经工作流的数据，在每个节点运行后捕获输入和输出。

**查看变量**：节点运行后输出出现在底部检查器面板，点击查看完整内容。

**编辑变量**：点击变量值进行编辑，下游节点使用时采用编辑后的值。不会更改创建节点的原始记录。

**重置变量**：还原图标恢复原始值；「全部重置」清除所有缓存变量。

##### 运行历史

每次工作流运行记录完整的日志。查看三个部分：
- **结果**：最终输出或错误消息（仅工作流应用）
- **详情**：原始输入、输出和执行系统元数据
- **追踪**：节点执行顺序、耗时、数据流向，适合调试分支和循环的复杂工作流

节点级历史：在节点配置面板点击「最后运行」查看最近的输入、输出和耗时。

##### 错误类型

**节点特定错误**：
| 节点 | 错误类型 | 原因 |
|------|---------|------|
| Code | CodeNodeError | Python/JS 代码执行异常 |
| Code | OutputValidationError | 输出数据类型与配置不匹配 |
| Code | DepthLimitError | 嵌套结构超过 5 层 |
| Code | CodeExecutionError | 沙箱服务未运行 |
| LLM | — | LLM 调用失败 |
| HTTP Request | — | HTTP 请求失败 |
| Tool | — | 工具执行失败 |

**系统级错误**：
| 错误类型 | 说明 |
|---------|------|
| InvokeConnectionError | 与外部服务的网络连接失败 |
| InvokeServerUnavailableError | 外部服务 503 或暂时停机 |
| InvokeRateLimitError | API 或模型的速率限制 |
| QuotaExceededError | 服务使用配额超限 |

##### 应用工具箱

构建器「功能」面板中开启的可选功能，不同应用类型支持的功能不同。

**对话开场白**：设置欢迎消息和建议问题，可插入变量（`{` 或 `/` 插入变量选择器，建议问题用 `{{variable_name}}`）。

**下一步问题建议**：回复后推荐下一步问题。可配置模型和自定义提示词（最长 1,000 字符）。

**文字转语音**：AI 回复转音频，支持自动播放。需配置工作区 TTS 模型。

**语音转文字**：聊天界面启用语音输入。需配置工作区 STT 模型。

**文件上传**：允许用户发送文件。可配置类型、方式和数量限制。自托管可通过环境变量调整：`UPLOAD_IMAGE_FILE_SIZE_LIMIT`（默认 10MB）、`UPLOAD_FILE_SIZE_LIMIT`（15MB）、`UPLOAD_AUDIO_FILE_SIZE_LIMIT`（50MB）、`UPLOAD_VIDEO_FILE_SIZE_LIMIT`（100MB）。

**引用与归属**：回复中展示知识库来源文档的编号引用。

**内容审核**：过滤不当内容。支持 OpenAI Moderation、关键词匹配、API 扩展三种方式。被标记时替换为预设回复。

**标注回复**：定义精选问答对，语义匹配超过阈值时直接返回而不调用 LLM。可在调试与预览/日志中添加标注，或在」日志与标注 > 标注管理「手动管理、批量导入导出问答对。可配置分数阈值和嵌入模型。

**生成更多类似内容**：为相同输入生成不同输出。每条结果最多 2 个变体，消耗额外 token。

##### 快捷键

构建器中可用快捷键提升效率。

**常规**：`Cmd/Ctrl + S` 发布，`Cmd/Ctrl + Z` 撤销，`Cmd/Ctrl + Shift + Z` 重做，`Cmd/Ctrl + C/V/X` 复制/粘贴/剪切选中节点，`Delete/Backspace` 删除选中节点。

**画布**：`Cmd/Ctrl + A` 全选节点，`Cmd/Ctrl + Shift + A` 取消全选，`Cmd/Ctrl + F` 搜索，`Cmd/Ctrl + D` 复制节点，`Cmd/Ctrl + /` 放大，`Cmd/Ctrl + -` 缩小，`Cmd/Ctrl + 0` 重置缩放。

##### 使用 MCP 工具

将 MCP 服务器的外部工具接入 Dify 应用。仅支持 HTTP 传输的 MCP 服务器。

**添加 MCP 服务器**：工作区 > 工具 > MCP > 添加 MCP 服务器 (HTTP)，填写服务器 URL、名称、图标、服务器 ID（唯一，小写字母/数字/下划线/连字符，≤24 字符，添加后不可更改）。

Dify 自动连接服务器、处理 OAuth 认证、获取工具列表。

**管理服务器**：更新工具（刷新新工具）、重新授权（修复过期令牌）、编辑设置（不可更改 ID）、移除（断开连接）。

**使用 MCP 工具**：出现在智能代理中（按服务器分组，如「Notion MCP » Create Page」）、工作流中（作为节点）、智能代理节点中。

**自定义工具**：可覆盖描述，为每个参数选择「自动」（AI 决定）或「固定」（设定值永不改变）。

**导出分享**：导出含服务器 ID，导入需配置相同 ID 的服务器。

##### 版本控制

对话流/工作流应用跟踪变更。三种状态：当前草稿（工作版本，用户不可见）、最新版本（用户实时版本）、历史版本（较旧的已发布版本）。

**发布版本**：点击发布 > 发布更新，草稿成为最新版本。

**查看版本**：历史图标查看所有版本，可按「所有版本」/「仅你的版本」/「仅命名版本」筛选。

**管理版本**：命名版本、编辑名称和发布说明、删除旧版本（不可删除当前草稿或最新版本）、恢复版本（替换当前草稿）。

##### 与团队成员协作

目前仅自托管可用，工作区成员实时编辑同一工作流，画布内评论讨论设计决策。

**实时编辑**：编辑权限及以上成员可同时编辑，最后编辑为准。

**评论**：右键 > 添加评论，或按 C 键进入评论模式，`@` 提及成员发送邮件通知，跨版本保留。查看需应用访问权限，添加/编辑/解决需编辑权限。

自托管需设置 `NEXT_PUBLIC_SOCKET_URL`；可通过 `ENABLE_COLLABORATION_MODE` 禁用。

##### 处理错误

LLM、HTTP、Code、Tool 节点支持预定义错误处理，三种行为：

- **无**（默认）：节点失败时不处理
- **默认值**：返回预设默认值，使用 `error_type` 和 `error_message` 变量
- **失败分支**：走独立分支逻辑

**循环/迭代节点中的错误**：
- 循环节点：任何子节点失败立即停止
- 迭代节点：`terminated`（默认，立即停止）、`continue-on-error`（跳过失败继续，失败项返回 null）、`remove-abnormal-output`（继续但过滤失败项，输出数组更短）

**错误变量**：`error_type` 和 `error_message`，可用于向用户显示消息、发送警报、选择恢复策略、记录调试日志。

## 发布

##### 分享你的 AI 应用

每个 Dify 应用构建完成后自动以多种方式提供服务。你可以选择最适合目标用户的方式交付。发布后所有渠道同时激活最新配置。

**核心流程**：
1. 在应用中点击「发布」以激活最新版本
2. 在发布部分找到 Web 应用链接
3. 将链接发送给用户，他们可以立即开始使用

**发布原理**：发布操作用当前配置替换实时应用，所有渠道立即生效：
- Web 应用立即更新新功能和响应
- API 端点提供最新的模型和工作流配置
- 嵌入式组件反映更新的样式和行为
- MCP 服务器提供对当前应用功能的访问

**发布前的必要配置**：
- **应用描述**：帮助用户了解你的应用功能
- **图标和品牌**：使应用易于识别且专业
- **访问控制**：决定公开还是需要身份验证
- **速率限制**：保护应用免受过度使用（尤其 API 访问）

所有发布方法使用相同的应用配置：设置一次，随处发布。

##### 工作流 Web App

工作流应用（DAG 有向无环图）的 Web 界面。与聊天应用不同，工作流应用设计用于产生特定输出的离散任务，不维护对话上下文。

**三种运行模式**：单次执行、批处理、结果管理。

**单次执行**：用户填写输入表单（基于起始变量）→ 点击运行（实时进度指示）→ 查看结果（复制、保存、反馈、生成类似内容按钮）。

**批处理**：通过 CSV 上传同时处理数百个输入。
1. 切换到「批量运行」标签
2. 下载 CSV 模板（自动包含所需的列结构）
3. 准备数据（每行对应一次工作流执行）
4. 上传并运行

批处理优势：并行执行、进度跟踪（实时更新）、全部导出为 CSV、失败的项目标记错误详情。CSV 文件必须使用 Unicode（UTF-8）编码。

**结果管理**：
- **保存结果**：用户点击「保存」→ 出现在「已保存」标签 → 跨会话持久保留 → 可随时访问
- **生成变体**：启用「生成类似内容」后，用户可基于成功结果生成变体，反复迭代直到满意

**应用场景**：文本生成、报告分析、批量内容生成、数据批量处理等。

##### 聊天 Web App

对话流应用（面向聊天助手/AI Agent）的 Web 界面。与工作流应用不同，聊天 Web App 保持对话记忆，让用户可以基于之前的交流继续构建。

**核心特性**：
- 跨会话对话上下文保持
- 继承对话流的所有编排设置
- 自适应移动端到桌面端
- 支持访问控制（如启用）

**对话前表单**：当对话流使用变量时，用户在开始聊天前需要完成一个表单，将上下文收集前置而非中断对话流程。每个表单字段都会增加摩擦，只询问必要信息。填完必填字段后「开始对话」按钮才会激活。

**交互功能**：
| 功能 | 说明 |
|------|------|
| AI 对话开场白 | 消除空白页面问题，AI 主动介绍自己并解释功能 |
| 复制按钮 | 一键复制 AI 回复 |
| 点赞/点踩反馈 | 帮助改进应用 |
| 后续问题建议 | 每次回复后自动生成 3 个上下文相关问题 |
| 语音输入 | 麦克风按钮 → 实时语音转文字 → 可编辑后发送（需浏览器麦克风权限） |
| 引用与归属 | 知识库引用来源显示在回复下方 |

**会话管理**：像现代消息应用一样管理多对话线程：新建（不丢失历史）、置顶重要对话、删除已完成对话。每个线程维护自己的记忆和上下文。

##### Web App 设置

Web App 设置控制已发布应用的外观和行为。修改设置后点击「发布」即立即生效。默认无需用户账户或登录即可工作，适合公共工具和演示。

**品牌与外观**：
- **应用标识**：设置名称、描述（≤160 字符，出现在着陆页和搜索结果）、图标（图片或表情符号，出现在浏览器标签页和收藏中）
- **视觉设计**：选择品牌颜色、主题（明亮/暗色）、布局选项。考虑受众偏好，在不同设备上测试效果
- **语言设置**：为目标受众配置界面语言
- **法律页面**：添加版权信息和隐私政策链接以符合合规

**功能继承**：Web App 自动包含应用配置中启用的功能。在编排中禁用某个功能会立即从发布的 Web App 中移除。自动继承的功能包括：
- 对话开场白和建议后续操作
- 对话前表单（用于上下文收集）
- 语音输入和语音转文字
- 来源引用与归属
- 反馈收集和评分
- 所有工作流步骤和 AI 模型配置
- 知识库集成和工具连接
- 自定义提示词和响应格式
- 速率限制和使用控制

**应用类型自适应**：
- **对话应用**：对话式界面，持久会话、对话管理、实时响应 → 客户支持、咨询工具、交互式助手
- **工作流应用**：表单输入界面，单次/批处理运行，结果管理 → 内容生成、数据分析、批处理

**发布前检查清单**：
1. 在不同设备和浏览器上测试运行
2. 配置名称、图标、描述和法律信息
3. 审查访问控制（公开/需认证）
4. 监控使用情况和反馈，根据反馈迭代

**访问控制**（需 Dify Enterprise 版）

默认新应用仅限特定团队成员访问。只有工作空间所有者、管理员和编辑者才能创建和发布 Web 应用。

从「工作室 → Web 应用访问权限」或编辑应用时的「发布」面板配置。提供四个访问级别：

| 级别 | 说明 | 典型场景 |
|------|------|----------|
| 平台内所有成员 | 工作空间任何成员凭密码/验证码/SSO 认证后访问 | 内部共享工具 |
| 平台内特定成员 | 限制给选定组或个人（新应用默认）。未选任何人则无人可访问，包括你自己 | 部门专用工具、敏感数据应用 |
| 已认证的外部用户 | 工作空间外用户通过 SSO 认证访问，管理员通过 IdP 管理 | 供应商/承包商/客户 AI 服务 |
| 任何人 | 无需身份验证，任何有 URL 者立即访问 | 公开演示、客户工具、开放资源 |

**按组 vs 按个人配置**：按组添加可实现自动权限管理——成员加入组自动获得访问，离开时自动撤销。工作空间所有者/管理员/编辑者始终可编辑应用，但需被明确添加到列表中才能使用已发布的 Web 应用。

##### 嵌入网站

将 Dify 应用嵌入到现有网站，用户无需离开当前页面即可使用 AI 助手。提供两种嵌入方式：聊天气泡（Script）和 Iframe。从「发布 → 嵌入」获取唯一令牌。

**方式一：聊天气泡（Script 嵌入）**

最受欢迎的方式——在网站添加可自定义的按钮，点击时打开 AI 助手。

```html
<!-- 配置 -->
<script>
window.difyChatbotConfig = {
  token: 'YOUR_TOKEN',                     // 必需：应用令牌
  isDev: false,                            // 开发环境标识
  baseUrl: 'https://udify.app',            // 自动基于 isDev 设置
  containerProps: {                        // 视觉自定义
    style: { right: '20px', bottom: '20px' },
    className: 'custom-chat-button'
  },
  draggable: false,                        // 允许拖动
  dragAxis: 'both',                        // 'x'、'y' 或 'both'
  inputs: {                                // 预填充用户上下文
    name: "John Doe",                      // 对应 Dify 应用变量名
    department: "Support"
  },
  systemVariables: {                       // 追踪系统变量
    user_id: 'USER_123',
    conversation_id: 'CONV_456'
  },
  userVariables: {                         // 用户资料信息
    avatar_url: 'https://example.com/avatar.jpg',
    name: 'John Doe'
  }
}
</script>
<!-- Dify 嵌入脚本 -->
<script src="https://udify.app/embed.min.js"></script>
```

**CSS 变量自定义聊天气泡按钮**：
```css
#dify-chatbot-bubble-button {
  --dify-chatbot-bubble-button-bottom: 1rem;
  --dify-chatbot-bubble-button-right: 1rem;
  --dify-chatbot-bubble-button-bg-color: #155EEF;
  --dify-chatbot-bubble-button-width: 50px;
  --dify-chatbot-bubble-button-height: 50px;
  --dify-chatbot-bubble-button-border-radius: 25px;
  --dify-chatbot-bubble-button-box-shadow: rgba(0,0,0,0.2) 0px 4px 8px 0px;
  --dify-chatbot-bubble-button-hover-transform: scale(1.1);
}
```

**inputs 支持四种类型**：
- `text-input`：接受任何值，超长截断
- `paragraph`：同上
- `number`：接受数字或数值字符串
- `options`：接受预设选项之一

使用 embed.js 时，输入值经过 GZIP 压缩 + base64 编码后附加到 URL，如 `http://localhost/chatbot/{token}?name=H4sIA...`

**方式二：Iframe 嵌入**

直接将 Dify 应用嵌入到网页内容中作为一部分。无需 JavaScript 的简单 HTML 实现：

```html
<!-- 基本嵌入 -->
<iframe 
  src="https://udify.app/chatbot/YOUR_APP_TOKEN"
  width="100%" 
  height="600"
  frameborder="0">
</iframe>

<!-- 自定义样式 -->
<iframe 
  src="https://udify.app/chatbot/YOUR_APP_TOKEN"
  width="400px" 
  height="500px"
  style="border: 1px solid #ccc; border-radius: 8px;">
</iframe>

<!-- 响应式设计 -->
<div style="position: relative; width: 100%; height: 0; padding-bottom: 75%;">
  <iframe 
    src="https://udify.app/chatbot/YOUR_APP_TOKEN"
    style="position: absolute; top: 0; left: 0; width: 100%; height: 100%;"
    frameborder="0">
  </iframe>
</div>
```

**Iframe 优势**：直接集成、完整功能、响应式、无需 JavaScript。

**应用场景**：
| 场景 | 推荐方式 | 说明 |
|------|----------|------|
| 客户支持 | 聊天气泡 | 放在显著位置，预填充页面/用户上下文 |
| 潜在客户挖掘 | Iframe 嵌入 | 直接在内容中嵌入资格表单 |
| 产品演示 | Iframe 嵌入 | 在着陆页展示 AI 功能 |
| 知识库 | 聊天气泡/Iframe | 替换静态 FAQ，用户获得个性化答案 |

**故障排查**：
- 聊天按钮未出现：检查令牌、确保脚本在配置之后加载、检查浏览器控制台 JS 错误
- Iframe 无法加载：确认 URL 令牌正确、检查网站是否允许 iframe 内容、确保父页面使用 HTTPS
- 与 Web 应用共享同一套配置

**使用场景**：
- 电商网站的智能客服助手
- SaaS 产品的帮助文档问答
- 企业官网的访客引导

##### MCP 服务器（发布）

将 Dify 应用发布为 MCP（Model Context Protocol）服务器，供 Claude Desktop、Cursor 等 AI 工具直接调用你的应用能力。

**基本原理**：Dify 应用作为 MCP 服务器暴露出工具函数，外部 AI 工具按需调用这些函数。例如，你的 Dify 应用实现了一个「分析代码库」工作流，Cursor 直接调用它就像调用内置工具一样。

**启用步骤**：
1. 进入应用的配置界面
2. 找到 MCP 服务器配置模块（默认禁用）
3. 开启开关，Dify 自动生成唯一的 MCP 服务器地址
4. 该地址包含身份验证凭据，需严格保密

**与 Claude Desktop 集成**：
1. 打开 Claude Desktop
2. 进入 Claude Profile > Settings > Integrations > Add integration
3. 填入你的 Dify 应用 MCP 服务器 URL
4. Claude Desktop 自动发现并加载可用工具

**与 Cursor 集成**：
1. 在项目根目录创建或编辑 `.cursor/mcp.json` 文件
2. 配置如下：

```json
{
  "mcpServers": {
    "your-dify-app-name": {
      "url": "https://your-dify-app-mcp-url"
    }
  }
}
```

3. Cursor 自动检测配置并将你的 Dify 应用作为工具提供
4. 可添加多个 Dify 应用（添加多个条目到 mcpServers 对象）

**安全注意事项**：
- MCP 服务器 URL 包含认证凭据，像对待 API 密钥一样保护它
- 怀疑泄露时使用「重新生成」按钮创建新的 URL
- 旧 URL 立即停止工作

**实用设计建议**：
- **描述性**：工具及其输入参数的描述要考虑 AI 如何解释。不要用「输入数据」，而是用「包含用户配置文件的 JSON 对象，必需字段：姓名、邮箱、偏好设置」
- **延迟**：MCP 负责通信层，但应用性能仍然重要。如果应用需要 30 秒处理，客户端会感受到同样的延迟。考虑添加进度指示器或将复杂工作流拆分为更小的操作

##### API 集成

通过后端即服务 API 将 Dify AI 能力嵌入现有产品，完全控制用户体验和数据流。

**为什么使用 Dify API**：
| 优势 | 说明 |
|------|------|
| 跳过后端复杂性 | 直接从前端应用访问 LLM 能力，无需管理 AI 基础设施 |
| 可视化应用管理 | 可视化设计和更新 AI 行为，更改立即同步到所有 API 消费者 |
| 提供商灵活性 | 在 AI 提供商间切换，集中管理 API 密钥，无需更改代码 |
| 内置监控 | 开箱即用的日志、分析和用户活动跟踪 |

**集成流程**：
1. **构建应用**：在 Dify Studio 中构建具有所需 AI 能力的应用
2. **生成 API 凭据**：应用 > API Access > 创建新的 API 密钥
3. **查看文档**：Dify 自动生成针对你应用配置的完整 API 文档
4. **集成到应用**：使用提供的示例将 API 调用集成到你的应用程序中

**API 安全最佳实践**：
- 永远不要在前端代码或客户端请求中暴露 API 密钥
- 始终从后端服务器调用 Dify API
- 为开发、测试、生产环境创建独立的 API 密钥
- 定期轮换密钥并撤销未使用的凭据
- 监控 API 使用情况检测异常活动
- 后端将 API 密钥存储为环境变量
- 实施你自己的速率限制和请求验证
- 记录 API 调用以便调试和监控

**文本生成 API**（适用于文本生成类应用）：

```bash
curl --location --request POST 'https://api.dify.ai/v1/completion-messages' \
--header 'Authorization: Bearer YOUR-SECRET-KEY' \
--header 'Content-Type: application/json' \
--data-raw '{
    "inputs": {},
    "response_mode": "streaming",
    "user": "abc-123"
}'
```

**关键参数说明**：
- `inputs`：传入应用的变量值，对应你在编排中配置的输入变量
- `response_mode`：`streaming`（流式返回，逐块输出）或 `blocking`（等待完整结果返回）
- `user`：用户标识符，用于区分不同用户

**对话 API**（适用于聊天助手/AI Agent 类应用）：

```bash
curl --location --request POST 'https://api.dify.ai/v1/chat-messages' \
--header 'Authorization: Bearer YOUR-SECRET-KEY' \
--header 'Content-Type: application/json' \
--data-raw '{
    "inputs": {},
    "query": "你好，请帮我查询订单状态",
    "response_mode": "streaming",
    "conversation_id": "",
    "user": "abc-123"
}'
```

**conversation_id 管理规则**：
| 场景 | 操作 |
|------|------|
| 新对话 | `conversation_id` 留空，系统生成并返回新的 ID |
| 继续对话 | 传入之前的 `conversation_id`，维持对话上下文 |
| 传入已有 conversation_id 时 | 新的 `inputs` 被忽略，只有 `query` 被处理 |
| 动态修改逻辑 | 使用会话变量（session variable）调整机器人行为 |

**重要提示**：服务 API 不会共享 WebApp 创建的对话。通过 API 创建的对话与在 WebApp 界面中创建的对话是隔离的。

**模板填写指南——关键字段规范**：

**语言要求**：名称、概述、设置步骤必须用英文撰写。应用内部文本（节点名称、提示词、展示给用户的消息）可使用任何语言（如中文）。若主要面向非英语用户，可在标题添加语言标签如 `[ZH]`。

**模板名称**：
- 简短英文短语，通常 3-7 个单词
- 格式为 `[渠道/目标] + [核心任务]`

**分类**：
- 仅选择 1-3 个最能描述模板的分类
- 不要为了增加曝光勾选所有分类（这会降低被目标用户发现的可能性）

**语言**：选择模板实际使用中面向的语言（即用例、输入或输出的语言），而非标题或概述的语言。

**概述**：
- 2-4 句英文
- 第 1 句：它做什么（一句话概括主要功能）
- 第 2-3 句：面向谁、什么场景（典型用户角色或场景：客服团队、营销人员、创始人、知识工作者等）
- 无需列出先决条件、输入或输出

**设置步骤**：
- Markdown 编号列表（1. 2. 3.）
- 每一步用简短的一句话，以动词开头
- 目标 3-8 步
- 标准顺序：使用/导入模板 → 连接账户/添加 API 密钥 → 连接数据源 → 可选自定义 → 激活工作流并运行测试
- 每一步回答：在界面中点击哪里、需要配置或填写什么

**提交前快速检查**：
- 名称是简短英文短语，清楚说明它在哪里运行、做什么
- 概述用 2-4 句英文解释价值和典型用例
- 仅选择了 1-3 个相关分类
- 设置步骤是清晰的编号列表
- 工作流内部的文本和提示词使用了面向目标用户的适当语言

## 监控

Dify 内置监控工具提供四个核心维度：仪表盘（宏观趋势）、日志（逐条交互详情）、标注系统（回复质量控制）、外部集成（深度可观测性）。

##### 仪表盘

仪表盘随时间追踪四个关键指标，以展示应用的宏观表现。使用时间选择器查看不同时间段的趋势变化。

| 指标 | 含义 | 用途 |
|------|------|------|
| Total Messages | 对话量 | 整体使用规模，衡量用户活跃度 |
| Active Users | 有意义的互动用户（交互 >1 次） | 排除只试一次就走的用户，反映真实留存 |
| Average User Interactions | 每次会话的参与深度（平均交互次数） | 用户粘性和对话质量指标 |
| Token Usage | Token 消耗量 | 资源成本和定价依据 |

**外部可观测性**：仪表盘右上角「Tracing app performance」入口可连接 Langfuse、LangSmith 等外部平台获取更深入分析。

**操作流程**：进入应用 → 监控 → 仪表盘 → 选择时间范围 → 查看四个指标曲线 → 如需深入分析，点击链接到外部可观测平台。

##### 日志

日志提供对每次交互的完整可见性，是调试和优化的核心工具。

**记录内容**：
- **完整对话历史**：用户输入 + AI 响应 + 时间线
- **系统上下文**：使用的模型、Token 消耗数、响应时间、处理中的错误/警告
- **用户反馈**：点赞/点踩评级、用户评论（与对话关联）
- **团队注释**：团队成员可在日志界面添加内部注释和改进后的响应

**排除项**：调试会话和提示词测试不包含在日志中。

**日志控制台功能**：
| 功能 | 说明 |
|------|------|
| 对话时间线 | 用户交互的时间顺序列表 |
| 消息详情 | 包含 AI 响应的完整对话上下文 |
| 性能数据 | 每次交互的响应时间和 Token 用量 |
| 用户反馈 | 来自用户和团队成员的评级和评论 |

**使用日志调试**：
1. **识别失败交互**：AI 提供不佳响应、未能理解用户意图、或遇到错误的对话
2. **发现性能问题**：慢响应、高 Token 消耗、系统错误
3. **用户旅程分析**：跟踪单个用户的多次对话，发现使用模式和痛点
4. **反馈分析**：识别常见投诉模式、成功的交互类型、改进领域

**数据保留**：
| 版本 | 保留期限 |
|------|----------|
| Sandbox | 30 天 |
| Professional / Team | 订阅期内无限期 |
| 自托管（默认） | 无限期 |
| 自托管（配置） | 通过环境变量控制：`WORKFLOW_LOG_CLEANUP_ENABLED`（启用）、`WORKFLOW_LOG_RETENTION_DAYS`（天数）、`WORKFLOW_LOG_CLEANUP_BATCH_SIZE`（批处理大小） |

**用日志改进应用**：
- **模式识别**：寻找应用处理不佳的重复问题 → 改进提示词或更新知识库
- **响应质量**：利用反馈模式识别哪些响应效果好、哪些需要完善
- **性能优化**：跟踪响应时间和 Token 消耗 → 优化提示词或模型配置
- **内容空白**：发现应用持续挣扎的主题 → 扩展知识库

**隐私注意事项**：日志包含完整用户对话（可能含敏感信息）。实施适当的访问控制并确保符合数据保护法规。可考虑配置更短保留期或实施日志匿名化。

##### 标注系统

为特定问题创建精心策划的完美回复库。当用户询问类似问题时，系统返回预先编写的答案而非 AI 生成内容，确保关键主题一致性并消除幻觉。

**适用场景**：
- **企业标准**：政策问题、产品信息、客服一致性高的场景
- **快速原型**：通过策划高质量响应快速改进演示应用，无需重新训练模型
- **质量保证**：确保敏感或重要问题始终收到认可的响应

**工作原理**：
```
用户提问 → 语义匹配标注库 → 超过相似度阈值？
  ├─ 是 → 返回策划的响应（快速通道）
  └─ 否 → 继续正常 AI 生成
```

**设置步骤**：
1. 进入编排 → 添加功能 → 启用「标注回复」
2. 配置两个关键参数：
   - **相似度阈值**：较高值需要更接近匹配。从中等设置开始，根据命中率调整
   - **文本嵌入模型**：用于向量化问题进行语义匹配。更改模型会重新生成所有嵌入向量

**三种创建标注方式**：
| 方式 | 步骤 |
|------|------|
| 从对话创建 | 在调试模式或日志中，编辑 AI 响应为完美答案 → 保存为标注 |
| 批量导入 | 下载模板 → 用指定格式创建问答对 → 上传批量创建 |
| 手动录入 | 在日志与标注界面直接添加标注（自定义问题+响应） |

**管理与分析**：
- **命中跟踪**：监控哪些标注被匹配、使用频率和相似度分数
- **持续改进**：回顾命中历史提高覆盖范围和准确性。持续错过标注的问题表明覆盖范围存在空白
- **A/B 测试**：比较实施标注前后的用户满意度衡量影响
- **命中率分析**：删除从未使用的标注，扩展成功模式
- **匹配质量**：检查相似度分数确保标注在适当问题上触发

**最佳实践**：
- 小步开始：从最常问的问题或必须准确的关键信息开始
- 测试阈值：实验相似度阈值，平衡匹配准确性和覆盖率
- 定期更新：标注会随时间过时，根据政策变化或用户反馈审查更新
- 标注作为 AI 生成的补充：处理已知案例的同时允许 AI 处理新颖问题

##### 概述

知识库将自有数据通过 RAG 技术集成到 Dify AI 应用中，为 LLM 提供特定领域的上下文信息，使回复更准确、相关，显著减少幻觉。RAG 流程：检索（从知识库检索相关信息）→ 增强（与用户问题打包为上下文）→ 生成（LLM 基于这些上下文生成精准答案）。可创建多个知识库分别适配不同领域/场景/数据源，按需集成到应用中。

**应用场景**：智能客服（产品文档/FAQ/故障排查）、企业内部知识门户（政策与流程查询）、内容生成（根据背景资料生成报告/文章/邮件）、科研分析（检索总结学术论文/市场报告/法律文档）。

**三种创建方式**：
1. 快速创建（导入数据 + 设置处理规则，简单高效，新手友好）
2. 知识流水线（自定义步骤和插件，编排复杂灵活的数据处理流程）
3. 连接外部知识库（通过 API 直接同步，无需迁移即可利用现有数据）

**管理与优化**：维护文档及其分段的增删改查 → 测试召回效果 → 利用元数据增强检索 → 调整索引方式/嵌入模型/检索策略。

##### 快速创建知识库

四步完成：
1. 知识库 → 创建知识库 → 选择数据源（上传本地文件/从 Notion 导入/从网页导入/空知识库）
2. 指定分段设置（见下方详解）
3. 指定索引方式和检索设置
4. 等待数据处理完成

**注意**：知识库创建后，数据源无法更改。

##### 上传本地文件

| 参数 | 限制 |
|------|------|
| 单次上传 | 最多 5 个文件 |
| Dify Cloud 批量上传 | 付费套餐支持，单次最多 50 个文件 |
| 单文件大小 | 最大 15 MB |
| 自托管调整 | 环境变量 `UPLOAD_FILE_SIZE_LIMIT` 和 `UPLOAD_FILE_BATCH_LIMIT` |

**图片提取规则**：
- JPG/JPEG/PNG/GIF 且 < 2MB 的图片自动提取到对应分段
- 每个分段最多 10 个图片附件
- 若索引设置中选择多模态嵌入模型（Vision 图标），提取图片也会被向量化索引
- 删除分段中的图片 URL 不影响已提取图片
- 支持 DOCX 嵌入图片、PDF 嵌入图片（需合适的文档提取插件）、Markdown 引用的 URL 图片 (`![alt](url)`)
- 自托管可通过 `ATTACHMENT_IMAGE_FILE_SIZE_LIMIT` 和 `SINGLE_CHUNK_ATTACHMENT_LIMIT` 调整限制

##### 从 Notion 导入数据

**授权**：创建知识库选择数据源时点击「同步自 Notion 内容 → 去绑定」完成 OAuth 授权。也可从「设置 → 数据来源 → 添加数据源」中绑定。

**导入**：完成授权后进入创建知识库页面 → 点击同步自 Notion 内容 → 选择需要的授权页面进行导入。

**支持**：普通类型页面 + database 类型下的页面属性（汇总保存）。暂不支持导入图片和文件，表格数据会被转换为文本展示。

**同步更新**：在文档列表页点击对应内容的「同步」按钮。同步涉及嵌入过程，会消耗嵌入模型的 Token。

**社区版 Notion 集成配置**：
- **Internal 集成**：在 Notion 创建内部集成 → 复制 Secrets → 配置 `.env`：`NOTION_INTEGRATION_TYPE=internal` + `NOTION_INTERNAL_SECRET=xxx`
- **Public 集成**：将 Internal 升级为 Public → 填写公司信息/重定向 URL → 配置 `.env`：`NOTION_INTEGRATION_TYPE=public` + `NOTION_CLIENT_SECRET=xxx` + `NOTION_CLIENT_ID=xxx`

##### 从网页导入数据

通过第三方工具抓取公开网页内容，解析为 Markdown 导入。支持两种 Provider：

**Firecrawl**：
1. DataSource 页面 → Firecrawl → Configure → 填入 API Key
2. 创建知识库 → Sync from website → Provider 选 Firecrawl → 填入 URL
3. 配置项：抓取子页面、页面数量上限、抓取深度、排除页面、仅抓取页面、提取内容
4. 点击 Run 预览目标页面，确认后导入

**Jina Reader**：
1. DataSource 页面 → Jina Reader → Configure → 填入 API Key
2. 创建知识库 → Sync from website → Provider 选 Jina Reader → 填入 URL
3. 配置项：抓取子页面、页面数量上限、使用 sitemap 抓取
4. 点击 Run 预览，确认后导入

两种工具均可点击 Add URL 继续添加新网页。

##### 指定分段设置

文档会被拆分为较小的片段（分段），系统在这些分段中搜索相关信息作为 LLM 上下文。

**关键参数**：
- **分隔符**：文本拆分依据（如 `\n\n` 在段落换行处拆分）。分隔符在分段过程中会被移除。为避免信息丢失，请使用文档中不会自然出现的非内容字符
- **分段最大长度**：每个分段的最大字符数，超限强制拆分
- **分段重叠长度**：相邻分段重叠的字符数，保持语义连接（如 50 字符重叠使分段边界信息不丢失）

**两种模式**：
| 维度 | 通用模式 | 父子模式 |
|------|---------|---------|
| 分段策略 | 单层：所有分段相同设置 | 双层：父分段和子分段分别设置 |
| 检索流程 | 匹配分段直接返回 | 子分段匹配查询，父分段返回提供更宽上下文 |
| 兼容索引 | 高质量、经济 | 仅高质量 |
| 适用场景 | 简单独立内容（术语表/FAQ） | 信息密集型文档（技术手册/研究论文），上下文很重要 |

知识库创建后分段模式不可更改，但分隔符和分段最大长度可随时调整。

**文本预处理**：替换连续空格/换行符/制表符（如 3+ 连续换行符 → 2 个，多空格 → 单空格，制表符/换页符/特殊 Unicode 空格 → 普通空格），可删除所有 URL 和电子邮件地址。此设置在全文模式下被忽略。

**摘要自动生成**（仅自托管）：自动为所有分段生成摘要并嵌入索引，摘要匹配时对应分段返回。可选择带视觉能力的 LLM，基于分段文本+图片生成摘要。

**预览分段**：点击预览查看内容如何被分段。多个文档时可切换文件名。

##### 指定索引方式与检索设置

索引方式直接影响 LLM 检索效率和回答准确性。

**索引方式**：
| 维度 | 高质量 | 经济 |
|------|--------|------|
| 原理 | 嵌入模型将内容分段向量化 | 关键词倒排索引 |
| 检索策略 | 向量检索 / 全文检索 / 混合检索 | 仅全文检索 |
| 权重设置 | 支持 | 不支持 |
| 切换 | 创建后不可切经济 | 可切高质量（需重新编码） |

**Q&A 模式**（仅自托管）：系统为每个分段生成 Q&A 匹配对，采用「Q to Q」（问题匹配问题）策略而非「Q to P」（问题匹配段落）。用户提问时找出最相似问题，返回对应分段作为答案。

**高质量索引的三种检索设置**：

1. **向量检索** — 向量化用户问题 → 与分段向量比较 → 找到最相邻分段
2. **全文检索** — 索引所有词汇 → 查询匹配包含词汇的文本片段
3. **混合检索** — 同时执行全文+向量检索 → Rerank 重排序选最佳匹配

可配置参数（需先启用 Rerank 模型才生效）：
| 参数 | 说明 | 默认值 |
|------|------|--------|
| Rerank 模型 | 第三方模型对结果重排序优化 | 关闭 |
| TopK | 返回相似度最高的分段数量，受模型上下文窗口限制动态调整 | 3 |
| Score 阈值 | 分段被检索的最低相似度分数 | 0.5 |

**多模态检索**：选择多模态嵌入模型（Vision 图标）可同时检索文本和图片。使用此类嵌入模型的知识库卡片标有 Multimodal。Rerank 也需对应多模态模型，否则图片在重排序中被排除。

##### 测试检索

知识库左侧边栏「检索测试」→ 输入模拟用户提问 → 查看召回结果。调整的检索设置仅临时生效，不影响知识库实际设置。

「记录」板块记录所有检索事件（测试检索 + 应用发起的检索请求），召回测试与常规检索共用 API。

##### 在应用内集成知识库

以聊天助手为例的操作流程：
1. 工作室 → 创建聊天助手
2. 上下文设置 → 添加 → 选择知识库 → 配置召回策略 → 元数据筛选
3. 开启引用和归属（在回复中显示来源）
4. 调试 → 发布

**召回模式（多知识库）**：在所有关联知识库中检索，通过 Rerank 策略排序最相关内容。

**Rerank 设置**：
| 方式 | 说明 | 成本 |
|------|------|------|
| 语义=1 | 纯语义检索（向量），跨语言查询 | 无额外成本 |
| 关键词=1 | 纯关键词匹配（全文），精确术语 | 低 |
| 自定义权重 | 手动调整语义/关键词比例 | 无 |
| Rerank 模型 | 外部模型评分排序，处理复杂内容 | 需额外 Token 费用 |

**元数据筛选**（知识检索节点）：
- **禁用模式**：不筛选
- **自动模式**：根据查询变量自动配置
- **手动模式**：自定义条件，支持字符串（is/is not/contains/not contains/starts with/ends with/empty）、数字（=/>/</≥/≤）、时间（is/before/after），筛选值可用变量或常量，条件之间支持 AND/OR

**常见问题**：
- 确切术语用关键词=1，跨语言用语义=1，需精确调整用自定义权重，复杂内容用 Rerank 模型
- 多个知识库嵌入模型不一致时无法调整权重设置，需统一检索设置或启用 Rerank 模型
- 「经济」索引模式不支持权重设置，需切换为「高质量」模式

只有工作区所有者、管理员和编辑者可修改知识库设置。在知识库中点击左侧边栏的「设置」图标进入设置页。

| 设置项 | 说明 |
|--------|------|
| 名称和图标 | 标识和区分知识库 |
| 描述 | 说明用途和内容 |
| 权限 | 定义哪些成员可访问，被授予者拥有全部内容维护权限 |
| 索引方式 | 决定文档分段的处理和组织方式 |

| 摘要自动生成 | 自托管可用，启用后新文档自动生成摘要；已有分段需手动在文档列表选择后点击「生成摘要」 |
| 检索设置 | 决定如何检索相关内容 |

##### 管理知识库内容

**管理文档**：知识库中每个导入项（本地文件/Notion/网页）都是一个文档。

| 操作 | 说明 |
|------|------|
| 添加 | 导入新文档 |
| 修改分段设置 | 可独立设置（不含分段结构），分段结构全库共享且创建后无法更改 |
| 删除 | 永久删除，不可撤销 |
| 启用/禁用 | 临时纳入或排除检索。Dify Cloud 上长时间未更新或未检索的文档会自动禁用（Sandbox 7 天，Pro/Team 30 天） |
| 生成摘要 | 自托管可用，自动生成所有分段摘要，覆盖已有 |
| 归档/取消归档 | 只读保留，可随时取消归档 |
| 编辑 | 编辑分段内容 |
| 重命名 | 修改文档名称 |

**管理分段**：文档根据分段设置拆分为分段，分段是检索的基本单元。

| 操作 | 说明 |
|------|------|
| 添加 | 新增或批量新增分段。父子模式可同时新增父+子分段。Dify Cloud 上为付费功能 |
| 删除 | 永久删除 |
| 启用/禁用 | 临时纳入/排除检索。禁用分段不可编辑 |
| 编辑 | 修改内容，已编辑分段标记为「已编辑」。父子模式中编辑父分段可选择重新生成子分段或保留；编辑子分段不改变父分段 |
| 添加/编辑/删除关键词 | 最多 10 个，仅经济索引模式可用 |
| 添加/删除图片附件 | 每个分段最多 10 张图片 |
| 添加/编辑/删除摘要 | 摘要被向量化索引，匹配时返回对应分段。多个分段用相同摘要可实现分组检索（受 TopK 限制） |

**最佳实践**：
- **检查分段质量**：分段过短上下文不完整，过长引入语义噪音，语义不完整导致内容缺失或误导
- **子分段作检索钩子**（父子模式）：将子分段改写为关键词、摘要或常见用户问题。例如 LED 状态指示灯的父分段，子分段可写为「闪烁灯、无法开机、红灯」
- **用摘要弥合查询与内容差距**：在语言不一致、概念隐含、原始内容为代码/表格等非文本、需要分组检索的场景下，摘要提供精简语义层

##### 管理文档元数据

元数据是「关于数据的数据」，为文档提供来源、用途等上下文信息，帮助快速查找和管理。

**元数据字段类型**：
| 维度 | 内置元数据 | 自定义元数据 |
|------|-----------|------------|
| 启用方式 | 默认禁用，手动开启 | 手动添加 |
| 生成方式 | 系统自动提取 | 用户自定义 |
| 修改权限 | 不可修改 | 可删除/编辑 |
| 应用范围 | 适用所有文档 | 需手动关联到文档 |
| 预定义字段 | document_name/uploader/upload_date/last_update_date/source | 用户自定义 |
| 值类型 | string/number/time | string/number/time |

**操作**：
- **新建字段**：点击「+添加元数据」→ 选择值类型（string/number/time）→ 填写名称（仅支持小写字母、数字、下划线）→ 保存
- **编辑字段**：点击编辑按钮仅支持修改名称，值类型不可改
- **删除字段**：点击删除将从全库所有文档中彻底移除该字段及值
- **批量编辑文档元数据**：勾选多个文档 → 下方操作栏点击「元数据」→ 可批量新增/修改/删除字段值。使用「应用于所有文档」选框控制改动是否对新文档生效
- **单篇编辑**：文档详情 →「开始标记」→ 进入编辑模式 → 添加/删改字段值

**FAQ**：元数据作用 — 提升搜索效率/增强数据安全/优化管理/支持自动化；管理列表中的字段是全库「字段定义」，文档中的值是具体「字段值」。

##### 通过 API 维护知识库

Dify 提供完整知识库 API，可通过编程方式管理知识库。创建知识库时 API 访问默认开启。

**获取凭据**：知识库页面右上角「服务 API」→ 获取端点 + 创建并管理 API 密钥。单个密钥可访问同一账号下所有可见知识库。

**关闭访问**：进入某知识库 → 左下角「访问 API」→ 关闭。

**API 参考**：完整端点列表/请求响应结构/错误码参见知识库 API 参考文档。

##### 连接外部知识库

将自建 RAG 系统或第三方知识服务（如 AWS Bedrock）集成到 Dify，无需迁移数据。

**三步流程**：
1. **构建检索 API**：实现外部知识库 API 规范的 POST 端点，接收搜索查询并返回匹配分段及相似度分数
2. **注册外部知识库 API**：前往知识库 → 右上角「外部知识库 API」→ 添加 → 填写名称/API 接口地址（Dify 自动追加 `/retrieval`）/API Key（Bearer 认证）→ 保存时测试连接
3. **创建外部知识库**：前往知识库 →「连接外部知识库」→ 填写名称/描述/选择已注册 API/填入外部知识库 ID（如 Bedrock ARN）→ 配置 TopK 和分数阈值

**限制**：外部知识库 API 和 ID 创建后不可更改。Dify 对外部知识库仅有检索权限。

**FAQ**：自托管环境 SSRF 代理阻止连接时，将服务域名加入 `docker/ssrf_proxy/squid.conf.template` 的 `allowed_domains` ACL 后重启容器。

##### 外部知识库 API 规范

外部知识服务必须实现的 API 协议。

**认证**：`Authorization: Bearer {API_KEY}`，认证逻辑由外部服务自行定义。

**请求**：`POST {endpoint}/retrieval`，`Content-Type: application/json`

**请求体**：
| 属性 | 必填 | 类型 | 说明 |
|------|------|------|------|
| knowledge_id | 是 | string | 外部系统知识源标识符 |
| query | 是 | string | 用户搜索查询 |
| retrieval_setting | 是 | object | 含 `top_k`(int) 和 `score_threshold`(float, 禁用时为 0.0) |
| metadata_condition | 否 | object | 元数据筛选条件，含 `logical_operator` (and/or) 和 `conditions` 数组 |

**响应**：HTTP 200，JSON 含 `records` 数组。

| 属性 | 类型 | 说明 |
|------|------|------|
| content | string | 文本分段，作为 LLM 上下文 |
| score | float | 相似度分数 (0-1) |
| title | string | 源文档标题 |
| metadata | object | 键值对，不能为 null |

**错误处理**：非 200 状态码触发错误。结构化错误返回 `error_code`(int) 和 `error_msg`(string)。建议：1001 无效 Authorization、1002 认证失败、2001 知识库不存在。

##### 知识流水线概述

知识流水线是构建文档处理流程的可视化解决方案，像编排工作流一样组合节点和工具，形成完整数据处理链路：

**数据源 → 数据提取 → 数据处理 → 知识库存储**

五个步骤：
1. 创建知识流水线
2. 编排知识流水线
3. 发布知识流水线
4. 上传文件
5. 管理和使用知识库

##### 步骤一：创建知识流水线

三种创建方式：

**从零开始**：点击空白知识流水线，按节点指引逐步配置。

**通过模板创建**：
| 模板名称 | 分段结构 | 索引方式 | 检索设置 | 说明 |
|---------|---------|---------|---------|------|
| 通用模式 | 通用 | 经济 | 倒排索引 | 简单位文档分割匹配 |
| 父子模式 | 父子 | 高质量 | 混合检索 | 精准匹配+上下文完整 |
| 简单问答 | 问答 | 高质量 | 向量搜索 | 结构化表格转问答 |
| 复杂 PDF | 父子 | 高质量 | 混合+加权评分 | 提取图片和表格 |
| LLM 上下文增强 | 父子 | 高质量 | 混合+加权评分 | 自动生成描述性注释 |
| Markdown 转换 | 父子 | 高质量 | 混合+加权评分 | Office 文件转 Markdown |
| LLM 生成问答 | 问答 | 高质量 | 向量+加权评分 | 自动生成问答对 |

**导入 DSL**：YAML 格式，包含数据源/处理流程/存储配置/节点连接/用户输入表单。

##### 步骤二：编排知识流水线

可视化拖放连接节点，将原始文档逐步转化为可搜索知识库。

**处理流程**：数据源配置 → 数据处理节点（提取器+分块器）→ 知识库节点（分段结构+索引配置）→ 用户输入表单 → 测试发布

**数据源配置**：
| 数据源 | 说明 | 配置要点 |
|--------|------|---------|
| 文件上传 | 本地文件上传 | 单次最多 50 个文件，每个 ≤15MB |
| Notion | 连接 Notion 工作区 | 可选开启提取器输出结构化内容或原始文本 |
| 网页爬虫 | Jina Reader/Firecrawl | URL/子页面/深度/排除路径等 |
| 在线网盘 | Google Drive/Dropbox/OneDrive | 自动检索，勾选导入 |

**数据处理节点**：

**文档提取器** — 识别读取文件，提取信息转换为下一节点可用格式。
- **Dify Extractor**：内置解析器，支持常见格式，从文档提取图片并返回 URL
- **Unstructured**：高度定制化策略（auto/hi_res/fast/OCR-only），元素级元数据

**分块器** — 将内容拆分为适合检索的片段：
| 类型 | 特点 | 使用场景 |
|------|------|---------|
| 通用分块器 | 固定大小，自定义分隔符 | 结构简单的基础文档 |
| 父子分块器 | 双层结构，子块匹配+父块上下文 | 需要完整上下文的复杂文档 |
| 问答处理器 | 处理 CSV/Excel 的 Q&A 对 | 结构化问答数据 |

**通用分块器设置**：分段标识符（默认 `\n`，支持正则）/ 分段最大长度 / 分段重叠长度。

**父子分块器设置**：父分块分隔符与最大长度 / 子分块分隔符与最大长度 / 父块模式（段落或完整文档）。

**问答处理器设置**：指定问题和答案所在的列。

**知识库节点配置**：
| 分段结构 | 可选索引方式 | 可用检索设置 |
|---------|------------|------------|
| 通用模式 | 高质量/经济 | 向量/全文/混合检索 / 倒排索引 |
| 父子模式 | 高质量（仅） | 向量/全文/混合检索 |
| 问答模式 | 高质量（仅） | 向量/全文/混合检索 |

多模态检索需选择 Vision 图标的嵌入模型 + 多模态 Rerank 模型。

**用户输入表单**：可创建非共享输入（每个数据源专用）或全局共享输入（所有节点可引用）。支持字段类型：文本/段落/下拉选项/布尔值/数字/单文件/文件列表。

**测试与发布**：
1. 检查配置完整性（点击「检查清单」）
2. 测试运行：导入一个文件 → 填写参数 → 运行查看历史记录和变量检查（每个节点的输入/输出）
3. 确认无误后发布（发布后分段结构不可修改）

##### 步骤三：发布知识流水线

发布后操作：
- **前往文档**：跳转到选择数据源上传文档
- **访问 API**：获取知识库 API 调用方法和说明
- **发布为流水线**：保存为可复用模板（Sandbox 不支持，需 Pro/Team）

##### 步骤四：上传文件

发布后通过弹窗的「前往文档」或下拉菜单的「去添加文档」进入。支持文件上传/在线网盘/Notion/网页爬虫四种数据源。如果编排中配置了用户输入字段，需在此步填写参数。预览分段后点击保存并处理，跟踪处理进度。

##### 步骤五：管理和使用知识库

创建后可在知识库管理界面浏览流水线编排并对节点和配置进行修改。日常维护包括文档更新、召回测试、修改流水线和知识库属性。

# 工作区

工作区是 Dify 中的基础组织单位。团队构建、配置和管理的一切都存在于工作区中，包括应用程序、知识库、团队成员、模型配置、插件和账单。

## 工作区概述

工作区包含并隔离组织所需的一切。每个资源都属于一个工作区。创建应用时，它会继承工作区的模型配置；添加团队成员时，他们根据角色获得资源访问权限；配置模型或安装插件时，它们对整个工作区可用。

```
工作区
├── 应用程序（聊天机器人、工作流、智能代理）
├── 知识库（文档、嵌入向量）
├── 团队成员（角色和权限）
├── 模型供应商（API 密钥、配置）
├── 工具和插件（集成、自定义代码）
└── 账单（订阅、限制、使用情况）
```

### 工作区角色

| 角色 | 权限范围 |
|------|---------|
| 所有者 | 控制账单、模型供应商和工作区设置 |
| 管理员 | 管理团队成员并配置模型/插件 |
| 编辑者 | 构建应用程序并管理知识库 |
| 成员 | 使用已发布的应用程序 |

Dify Cloud 在首次登录时自动创建工作区。社区版在安装过程中创建。个人账户可属于多个工作区，使用左上角选择器切换。

## 模型供应商

模型供应商为工作区提供 AI 模型访问。有两种类型：

| 类型 | 管理方 | 计费 | 适用场景 |
|------|--------|------|---------|
| 系统供应商 | Dify 管理 | Dify 订阅计费 | 快速入门、原型设计 |
| 自定义供应商 | 用户自己的 API 密钥 | 直接向供应商付费 | 生产应用、更高速率限制 |

可同时使用两种方式。

### 配置自定义供应商

只有工作区管理员和所有者可配置。流程：
1. 导航至设置 → 模型供应商
2. 选择供应商（OpenAI、Anthropic、Google、Cohere、Ollama 等）
3. 添加凭据（API 密钥及所需配置）
4. 测试并保存

**支持的模型类型**：
- 大型语言模型：OpenAI（GPT-4、GPT-3.5-turbo）、Anthropic（Claude）、Google（Gemini）、Cohere、Ollama 本地模型
- 文本嵌入：OpenAI Embeddings、Cohere Embeddings、Azure OpenAI、本地嵌入模型
- 专用模型：图像生成（DALL-E、Stable Diffusion）、语音（Whisper、ElevenLabs）、内容审核 API

### 管理模型凭据

可为预定义模型和自定义模型添加多个凭据：

```yaml
推荐多凭据场景：
  环境隔离: 开发/测试/生产用不同凭据
  成本优化: 最大化利用免费或低成本额度
  模型实验: 不同模型版本快速切换
```

操作入口：供应商面板右上角「配置」→ 添加/修改/删除凭据，或选择默认凭据。

### 负载均衡（付费特性）

需订阅 SaaS 付费服务或购买企业版。采用轮询策略，将请求分配至多个凭据。

```python
# 负载均衡工作机制
策略 = "轮询（Round Robin）"
if 凭据触发速率限制:
    暂时跳过（1 分钟内不再分配给该凭据）
```

配置步骤：
1. 点击目标模型「配置」→ 选择「负载均衡」模式
2. 在负载均衡池中添加至少 2 个凭据
3. 可重复添加某凭据以增加权重
4. 点击保存

切换回单凭据模式时保留负载均衡配置备用。

### 故障排除

| 问题 | 排查方向 |
|------|---------|
| 身份验证失败 | 验证 API 密钥准确性、过期时间、积分余额、密钥权限 |
| 模型不可用 | 检查供应商配置是否包含该模型、API 密钥等级权限、刷新设置 |
| 速率限制 | 升级供应商账户、实施请求队列、使用自定义供应商 |

## 插件

插件是扩展工作区能力的模块化组件——模型提供商、外部 API、自定义工具。安装一次即可在所有地方使用。

### 插件安装来源

| 来源 | 说明 |
|------|------|
| 应用市场 | 官方和合作伙伴插件，经过测试和维护 |
| GitHub | 使用 URL + 版本从公共仓库安装 |
| 本地上传 | 自定义 .zip 包，用于私有或内部插件 |

### 插件权限

团队成员根据角色访问插件：
- **所有者和管理员**：为整个工作区安装、配置和移除插件
- **编辑者和成员**：使用已安装的插件

### 插件类型

插件是 Dify 与外部世界之间的桥梁：
- **模型提供商**：Dify 中的每个 LLM 实际上都是一个插件
- **工具和函数**：API 调用、数据处理、计算
- **自定义端点**：将 Dify 应用公开为 API
- **反向调用**：插件可回调 Dify 来使用模型、工具或工作流

### 企业版安装限制

企业工作区中管理员可控制：
- 插件来源（市场、GitHub、本地文件）
- 插件类型（官方、合作伙伴、第三方）
- 安装确认对话框指示策略阻止情况

### 构建自定义插件

使用 Dify SDK：
1. 设置 → 插件 → 调试获取调试密钥
2. 本地构建和测试
3. 打包为 .zip（含清单和依赖项）
4. 私下分发或发布到市场

Dify 工具使 LLM 能够与外部服务和 API 交互，访问实时数据并执行操作。

### 工具使用场景

## 管理应用

### 应用组织

| 操作 | 说明 |
|------|------|

| 导入/导出 DSL | 在工作区之间共享应用 |

### 导出 DSL

入口：Studio 页面菜单「导出 DSL」或编排页面左上角「导出 DSL」。

**不导出内容**：

### 导入 DSL

1. 上传 DSL 文件（YAML 格式）
2. 系统检查版本兼容性
3. 使用配置创建应用

### 命名最佳实践

```yaml
命名约定:
  - 描述性名称

  - 定期清理测试和未使用应用

```

删除后：所有配置、提示词、工作流、使用日志、已发布 Web 应用和 API 访问、用户对话和数据即刻丢失且不可撤销。

## API 扩展

API 扩展通过自定义 API 扩展 Dify 模块能力。目前支持的扩展类型：
- **moderation**：敏感内容审核
- **external_data_tool**：外部数据工具

### API 规范

Dify 以以下方式调用接口：

```yaml
请求方法: POST {Your-API-Endpoint}

请求头:
  Content-Type: application/json
  Authorization: Bearer {api_key}

请求体:
  point: string    # 扩展点标识
  params: {}       # 扩展点参数

响应:
  # 根据模块不同而异
```

### 验证机制

配置时 Dify 发送验证请求：

```json
// 请求
{
    "point": "ping"
}

// 预期响应
{
    "result": "pong"
}
```

### 外部数据工具（External Data Tool）

**扩展点**：`app.external_data_tool.query`

将用户输入的变量和对话内容传递给外部 API，获取结果后拼入提示词作为 LLM 的额外上下文。

```json
// 请求示例
{
    "point": "app.external_data_tool.query",
    "params": {
        "app_id": "61248ab4-1125-45be-ae32-0ce91334d021",
        "tool_variable": "weather_retrieve",
        "inputs": {"location": "London"},
        "query": "How's the weather today?"
    }
}

// 响应
{
    "result": "City: London\nTemperature: 10°C\n..."
}
```

### 敏感内容审核（Moderation）

两个扩展点：

| 扩展点 | 用途 | 触发时机 |
|--------|------|---------|
| `app.moderation.input` | 用户输入内容审核 | 启用内容审核 > 审核输入内容时 |
| `app.moderation.output` | LLM 输出内容审核 | 启用内容审核 > 审核输出内容时 |

输出内容为流式时，每 100 字符分段请求以降低延迟。

### app.moderation.input 请求

```yaml
point: app.moderation.input
params:
  app_id: string     # 应用 ID
  inputs: {}         # 用户输入变量
  query: string|null # 对话输入内容
```

```json
// 请求示例
{
    "point": "app.moderation.input",
    "params": {
        "app_id": "61248ab4-1125-45be-ae32-0ce91334d021",
        "inputs": {
            "var_1": "My SSN is 123-45-6789.",
            "var_2": "My phone number is 123-456-7890."
        },
        "query": "Please help me update my account."
    }
}

// 响应示例（action=direct_output）
{
    "flagged": true,
    "action": "direct_output",
    "preset_response": "Your content violates our usage policy."
}

// 响应示例（action=overridden）
{
    "flagged": true,
    "action": "overridden",
    "inputs": {
        "var_1": "My SSN is ***-**-****.",
        "var_2": "My phone number is ***-***-****."
    },
    "query": "Please help me update my account."
}
```

| 响应字段 | 类型 | 说明 |
|---------|------|------|
| `flagged` | bool | 是否违反规则 |
| `action` | string | `direct_output`（直接输出预设响应）或 `overridden`（覆盖变量值） |
| `preset_response` | string | 预设响应（仅 `direct_output`） |
| `inputs` | object | 覆盖后的变量值（仅 `overridden`） |
| `query` | string|null | 覆盖后的对话输入（仅 `overridden`） |

### app.moderation.output 请求

```yaml
point: app.moderation.output
params:
  app_id: string  # 应用 ID
  text: string    # LLM 响应内容（流式时每 100 字符分段）
```

```json
// 请求示例
{
    "point": "app.moderation.output",
    "params": {
        "app_id": "61248ab4-1125-45be-ae32-0ce91334d021",
        "text": "My SSN is 123-45-6789."
    }
}

// 响应（action=direct_output）
{
    "flagged": true,
    "action": "direct_output",
    "preset_response": "Your content violates our usage policy."
}

// 响应（action=overridden）
{
    "flagged": true,
    "action": "overridden",
    "text": "My SSN is ***-**-****."
}
```

| 响应字段 | 类型 | 说明 |
|---------|------|------|
| `flagged` | bool | 是否违反规则 |
| `action` | string | `direct_output` 或 `overridden` |
| `preset_response` | string | 预设响应（仅 `direct_output`） |
| `text` | string | 覆盖后的 LLM 响应（仅 `overridden`） |

### 完整 API 扩展代码示例（Python FastAPI）

```python
from fastapi import FastAPI, Body, HTTPException, Header
from pydantic import BaseModel

app = FastAPI()

class InputData(BaseModel):
    point: str
    params: dict = {}

@app.post("/api/dify/receive")
async def dify_receive(data: InputData = Body(...), authorization: str = Header(None)):
    expected_api_key = "123456"
    auth_scheme, _, api_key = authorization.partition(' ')

    if auth_scheme.lower() != "bearer" or api_key != expected_api_key:
        raise HTTPException(status_code=401, detail="Unauthorized")

    point = data.point

    if point == "ping":
        return {"result": "pong"}
    if point == "app.external_data_tool.query":
        return handle_external_data_tool(params=data.params)

    raise HTTPException(status_code=400, detail="Not implemented")
```

## 简单聊天机器人（Hello World）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/simple-chatbot

**教程目标**：用最少的步骤构建一个对用户问题分类 + 回答 + 有趣事实增强的聊天机器人。

### 应用概览

```
用户提问 → LLM（分类&回答，结构化输出） → 代码（查找趣事） → 答案（最终输出）
```

### 步骤 1：创建工作流（2 分钟）

工作室 > 工作流 > 从空白创建 > 编排 > 新建对话流 > 创建

### 步骤 2：添加工作流节点

**技巧**：输入 `{` 或 `/` 即可引用变量。

#### 2.1 LLM 节点：理解并回答问题

| 配置项 | 值 |
|-------|-----|
| 模型 | 选择任一 Chat 模型 |
| System Prompt | 见下方 |
| 结构化输出 | 开启，从 JSON 导入 schema |

**System Prompt:**
```
用户将询问关于某个国家的问题。问题是 {{sys.query}}
任务：
1. 识别提到的国家。
2. 清晰地重新表述问题。
3. 使用常识知识回答问题。

以以下 JSON 格式响应：
{
  "country": "<国家名称>",
  "question": "<重新表述的问题>",
  "answer": "<对问题的直接回答>"
}
```

**结构化输出 JSON Schema:**
```json
{
  "country": "string",
  "question": "string",
  "answer": "string"
}
```

**作用**：结构化输出让 LLM 返回一致的、机器可读的结果，便于下游节点精确提取或条件判断。

#### 2.2 代码节点：获取趣事

| 配置项 | 值 |
|-------|-----|
| 输入变量 | `country` ← `structured_output > country` |
| 输出变量 | 重命名为 `fun_fact` |

```python
def main(country: str) -> dict:
  country_name = country.lower()
  fun_facts = {
    "japan": "日本有超过 500 万台自动售货机。",
    "france": "法国是世界上访问量最大的国家。",
    "italy": "意大利拥有的联合国教科文组织世界遗产地比任何其他国家都多。"
  }
  fun_fact = fun_facts.get(country_name, f"没有关于 {country.title()} 的趣事。")
  return {"fun_fact": fun_fact}
```

#### 2.3 答案节点：给用户的最终答案

```
问：{{ structured_output.question }}

答：{{ structured_output.answer }}

趣事：{{ fun_fact }}
```

### 步骤 3：测试（3 分钟）

点击预览，输入如"法国的首都是什么？"、"给我介绍一下日本料理"等测试。

### 关键要点

| 知识点 | 说明 |
|-------|------|
| 结构化输出 | 控制 LLM 返回格式，下游节点可精确提取 |
| 代码节点 | 在可视化工作流中注入 Python 逻辑 |
| 变量引用 | `{` 或 `/` 唤起变量菜单 |

## 使用知识库搭建智能客服机器人

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/customer-service-bot

**教程目标**：搭建基于知识库的智能客服，解决传统关键词检索机器人无法理解的语义级问题。

### 本实验知识点

- Chatflow 基础使用
- 知识库、外部知识库的使用
- Embedding 的概念

### 核心概念：Embedding

**Embedding** 是将离散型变量（单词、句子、整个文档）转化为连续向量表示的技术。语义相似文本向量相近，语义相反的向量相反。LLM 使用这些向量数据做训练，预测后续向量从而生成文本。

### 前提条件

1. 创建空白应用 - 工作流编排（Chatflow 类型）
2. 添加 Embedding 模型供应商（OpenAI、Cohere 等有 TEXT EMBEDDING 标签的）

### 搭建流程

#### 1. 创建知识库

知识库 > 选择数据源 → 三种数据源：

| 数据源 | 限制 |
|-------|------|
| 上传文本文件 | 文件类型/大小限制 |
| 同步 Notion | 需绑定 Notion 账号 |
| 同步 Web 站点 | 需 Jina/Firecrawl API（最多 50 页） |

#### 2. 分段设置

- **自动分段与清洗**：Dify 自动按文本内容切分为段落
- **自定义**：手动设置切分规则（分段长度、重叠度等）

#### 3. 索引方式

| 模式 | 特点 |
|------|------|
| 高质量 | 额外消耗 Token，检索更精准 |
| 经济 | 不消耗 Token，牺牲一定准确性 |
| Q&A 分段 | 社区版，将文本整理为问答格式，消耗 Token |

#### 4. Embedding 模型选择

不同模型适用不同场景：
- Cohere `embed-english`：英文文档
- Cohere `embed-multilingual`：多语言文档

#### 5. 检索设置

三种检索功能：

| 类型 | 说明 |
|------|------|
| 向量检索 | 语义为主 |
| 全文检索 | 关键词为主 |
| 混合检索 | 语义 + 关键词，可设权重（如语义70%/关键词30%） |

**Rerank（重新排序）**：可选，使用 Rerank 模型对检索结果二次排序。

#### 6. 节点编排

```
开始 → 问题分类节点 → 分支1: 无关问题 → 直接回复
                     → 分支2: Dify相关问题 → 知识检索 → LLM → 直接回复
                     → 分支3: 技术名词解释 → 知识检索 → LLM → 直接回复
                     → 分支4: 社群加入方式 → 直接回复
```

**问题分类节点**：选择更优秀的 LLM，分类需足够具体、区分度大。

**直接回复节点**：支持 Markdown 格式输出，可嵌入图片。

**知识检索节点**：勾选已创建的知识库，LLM 以检索结果为上下文回答问题。

**LLM 记忆**：开启后对话体验更连贯。

### 思考题

**1. 连接外部知识库**：通过外部知识库 API 连接 AWS Bedrock 等外部源。

**2. API 管理知识库**：知识库 > API > 创建 API 密钥，通过 API 增删查状态。

**3. 嵌入网页**：发布后 > 嵌入网页 > 选择嵌入形式 > 粘贴代码。

### 核心认知

> 知识库的核心是检索而非 LLM。LLM 增强了输出过程，但真正的需求仍然是生成答案。上下文窗口是指 LLM 能"看到"和"记住"的文字范围，窗口越大，能利用的上下文信息越多。

添加文件变量，类型为文档。

**关键认知**：LLM 无法直接读取文件。必须先经过文档提取器将文件转为文本变量。


#### LLM 节点 1：结构提取

从原文内容中提取文章结构，总结关键内容。

完整 Prompt 示例包括：
- 主要目标：全面解析文章的结构
- 要求：详细说明每个部分的内容
- 预期输出：文章结构的详细解析
- 推理顺序：识别结构 → 提供具体内容
- 输出格式：Markdown，每个部分以标题列出
- 边缘情况处理

#### LLM 节点 2：问题抛出

从结构提取的总结中提炼问题。

完整 Prompt 示例包括：
- 主要目标：针对文章各部分提出尽可能多的问题
- 要求：问题有意义和价值，值得思考
- 输出格式：每个问题单独成行，编号列出

### 思考题

**1. 处理多个上传文件**

```
开始（文件变量为 Array 类型） → 迭代 → [子流程：文档提取器 → LLM结构提取 → LLM问题抛出] → 回复
```

**迭代节点**：类似编程中的 `while`，但 Dify 中无条件限制，输入必须是 Array 类型。Dify 会将列表中所有内容执行完为止。

**2. 只处理文件列表的特定文件**

在迭代前加入**列表操作**节点：

| 操作 | 说明 |
|------|------|
| 过滤 | 限定只处理文档类型文件 |
| 排序 | 按文件名排序 |
| 截取 | 只取前 N 个 |

列表操作可对所有 Array 类型变量操作（不仅是文件列表）。

## Workflow 101 系列（十课）

Workflow 101 是一套循序渐进的 10 课教程，通过搭建一个 **AI 邮件助理** 贯穿始终，从零开始逐步掌握 Dify 工作流的所有核心概念。

### 第 1 课：什么是工作流

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-01

#### 核心概念

**工作流的类比**：就像菜谱——
- 材料（输入）：需要准备什么？
- 步骤（过程）：每一步需要做什么？
- 成品（输出）：最后做出什么菜？

```
闹钟响 → 关闹钟 → 穿衣服 → 洗漱 → 吃早餐
```

#### 工作流三要素

| 要素 | 说明 |
|------|------|
| 输入 | 提供给 AI 的信息（问题、文章等） |
| 过程 | AI 按顺序依次完成的任务 |
| 输出 | AI 最终生成的结果 |

#### 节点

每个环节就是一个**节点**，各司其职，像接力赛一样：

| 节点类型 | 功能 |
|---------|------|
| LLM | 大模型节点 |

| 条件分支 | 路由分流 |
| 工具 | 外部能力 |

通过选择和拖拽连接节点，像搭积木一样构建工作流。

#### 动手实践

1. 注册 Dify 账号
2. 探索页面 → 查看标记为"工作流"的应用模板

### 第 4 课：小抄（知识检索）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-04

#### 问题

AI 会出现**幻觉（Hallucination）**——一本正经地胡说八道。需要给它一本"小抄"。

#### RAG（检索增强生成）

| 步骤 | 说明 | 类比 |
|------|------|------|
| 检索（Retrieval） | 从知识库中检索最相关的信息 | 找到菜谱 |
| 增强（Augmented） | 将检索结果与用户问题组合成新 Prompt | 把菜谱放手边 |
| 生成（Generation） | 基于新 Prompt 生成有事实依据的回答 | 按菜谱烹饪 |

#### 知识检索节点

在开始和 LLM 节点之间插入，以客户邮件原文作为搜索关键词去知识库查找匹配信息。

#### 动手实践 1：创建知识库

1. 知识库 → 创建知识库 → 上传本地文件
2. **分段设置**：通用模式，自动切分
3. **索引方式**：
   - 高质量：消耗 Token，检索精准
   - 经济：不消耗 Token，结构简单文本可用
4. **检索设置**：
   - 经济模式下仅支持**倒排索引**（类似实体书背面的索引页）
   - Top K：默认 3，控制检索返回的卡片数量
5. 保存并处理

#### 动手实践 2：添加知识检索节点

1. 在开始和 LLM 之间插入知识检索节点
2. 连接知识库：添加 What's Dify
3. **查询文本**：设置为 `email_content`（告诉 AI 用客户消息作为搜索关键词）
4. 如果没有设置查询文本，AI 就像盯着一本合上的书

#### 动手实践 3：升级 AI

**LLM 节点**：
- 上下文（Context）：选择知识检索的 `result`
- Prompt 中用 `/` 插入上下文变量

#### 作用验证

测试包含知识库相关内容的邮件（如问 Dify 的含义），AI 回复将依据知识库内容而非凭空想象。

### 第 5 课：工作流的岔路口（分类与执行）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-05

#### 问题

不同邮件需要不同处理方式（产品询问 vs BUG 提交）。需要"看人下菜碟"。

#### 条件分支（If/Else）节点

**判断条件类型**：

| 条件 | 说明 |
|------|------|
| 是 / 不是 | 完全等于或不等于某个值 |
| 包含 / 不包含 | 文本中是否含有关键词 |
| 开始是 / 结束是 | 文本的开头或结尾 |
| 为空 / 不为空 | 变量有无内容（如是否上传附件） |

#### 动手实践

**1. 添加条件分支**：IF `email_content` 包含 "Dify"

**2. 规划路径**：
- **IF 分支**：连接知识检索流程（专业回复）
- **ELSE 分支**：新建 LLM 节点 → 通用礼貌回复

**ELSE 分支 Prompt：**
```
You are a professional customer service manager. Based on the customer's email, kindly inform the user that no relevant information was found and provide relevant guidance.
Requirements:
1. Address the customer name in a friendly tone.
2. Thank them for their letter.
3. Keep the tone professional and friendly.
4. Sign off as "Anne."
```

#### 变量聚合器

漏斗/交通枢纽——无论上游有多少分支，都能汇集到一个出口。

**使用步骤**：
1. 删除结束节点与 LLM 的连线
2. 添加变量聚合节点
3. 两个 LLM 的输出都连入聚合器
4. 输出节点改为聚合器的输出

#### 最终工作流

```
开始 → 条件分支 → [IF: 知识检索 → LLM] → 变量聚合器 → 结束
                 → [ELSE: LLM2] ────────────→ ┘
```

### 第 6 课：处理多个任务（参数提取 & 迭代）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-06

#### 问题

一封邮件包含多个独立问题，AI 可能只回答第一个或混合回答。

#### 参数提取器

像信息搜集员，阅读文本并根据规则提取所有关键信息。

**参数类型**：

| 类型 | 用途 | 例子 |
|------|------|------|
| String | 单个文本 | 一个客户名字 |
| Number | 单个数字 | 订单数量 |
| Boolean | 是/否判断 | 是否已激活 |
| Array[String] | **文本列表** | 邮件中所有问题 |
| Array[Number] | 数字列表 | 所有商品价格 |
| Array[Boolean] | 布尔列表 | 多项是否完成 |
| Array[Object] | 对象列表 | 姓名+电话的通讯录 |

#### 动手实践 1：参数提取

1. 移除旧节点（知识检索、条件分支、LLM、变量聚合器）
2. 添加参数提取器，输入变量 = `email_content`
3. 创建提取参数：
   - 名称：`question_list`
   - 类型：`Array[String]`
   - 描述：用户在邮件中提出的所有问题
4. 指令：`请从文本中提取所有独立的问题，每一个问题作为列表中的一项。`

#### 迭代节点

给助理配备分身，对列表中每个项目执行相同的子流程。

**高级选项**：

| 选项 | 说明 |
|------|------|
| 并行模式（默认关闭）| 开启后同时处理所有项（类似 5 个厨师同时炒 5 个菜）|
| 错误时终止 | 任何一项失败则停止 |
| 忽略错误并继续 | 跳过失败的项继续处理 |
| 移除错误输出 | 从结果列表中移除失败项 |

**迭代中的 `item`**：特指当前正在处理的列表项。

#### 动手实践 2：配置迭代

1. 添加迭代节点，输入 = `question_list`
2. 迭代内部：知识检索（查询变量 = `item`）→ LLM（上下文 = 检索结果）
3. 迭代输出变量 = LLM 的 text
4. 迭代后加 LLM 2 汇总所有答案成一封完整邮件
5. 输出节点连接 LLM 2

#### 最终工作流

```
开始 → 参数提取(question_list) → 迭代 → [知识检索 → LLM] → LLM-汇总 → 输出
```

### 第 7 课：增强工作流（插件）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-07

#### 问题

知识库里没有的最新问题（如"最近有什么新功能？"），需要上网搜索。

#### 工具和 Dify Marketplace

在 Dify Marketplace 中安装官方或社区提供的工具（插件），扩展工作流能力。

#### 动手实践：升级迭代子流程

**最终效果**：
```
迭代 item → 知识检索 → LLM-判断 → 条件分支 → [IF: 知识库不够 → Google搜索 → LLM-搜索回答]
                                        → [ELSE: 知识库够 → LLM-知识库回答]
                                     → 变量聚合器
```

#### 第一步：知识库查询和判断

LLM 判断节点（知识检索后）：
```
System: Based on the `Context`, determine if the answer contains enough information to answer the questions. If the information is insufficient, you MUST reply with: "Information not found in knowledge base".
```

#### 第二步：判断是否需要搜索

- 条件：IF LLM.text 包含 "Information not found in knowledge base"
- IF 分支：添加 Google 搜索工具（需从 Marketplace 安装 + 配置 SerpAPI Key）
- ELSE 分支：LLM 基于知识库回答

**GET API Key**：SerpAPI 注册获取 → 回到 Dify 填凭据 → 查询字段选择 `Iteration/{item}`

#### 第三步：汇总输出

1. 迭代输出变量 = 变量聚合器的 output
2. 迭代后 LLM 总结所有答案
3. 输出节点连接总结 LLM

### 第 8 课：Agent 节点

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-08

#### Agentic Workflow

不再是简单"输入→处理→输出"，而是包含思考、规划、使用工具、根据结果调整的智能流程。

#### Agent 策略

| 策略 | 说明 |
|------|------|
| **ReAct** (Reason + Act) | 边思考边行动：思考→行动→观察结果→再思考（本课选择） |
| Plan-and-Execute | 先制定详细计划，再严格执行 |
| Chain of Thought (CoT) | 先一步步推理，提高答案准确性 |
| Self-Correction | AI 审视评估自己的初步结果并修正 |
| Memory | 短期或长期记忆机制 |

#### Agent 节点

高度封装的智能单元——给定目标 + 工具 → 内部自主思考、规划、调用工具。

#### 动手实践：用 Agent 节点重构

**关键配置**：
1. 保留知识检索节点，移除迭代内其他节点
2. 添加 Agent 节点
3. 从 Marketplace 安装 "Dify Agent 策略" 插件
4. 选择 ReAct 策略
5. **模型必须支持 Function Calling**（如 gpt-5），否则 Agent 无法调用工具
6. 添加工具：Google Search
7. **指令模板**：

```
Goal: Answer user questions about Dify products.

Steps:
1. I have provided a relevant internal knowledge base retrieval result. First, judge if this result can fully answer the user's questions.
2. If the context clearly answers it, generate the final answer based on the context.
3. If the answer is insufficient or irrelevant, use the Google Search tool to find the latest information and generate the answer based on search results.

Requirement: Keep the final answer concise and accurate.
```

8. 上下文：知识检索 result Array[Object]
9. 查询：`Iteration/{x} item`（聚焦当前问题）
10. 迭代输出：Agent text

#### 为什么选择 ReAct？

允许 Agent 先推理（Reason）→ 行动（Act）→ 观察结果 → 再推理，非常适合动态决策和多工具协作的复杂任务。

#### 为什么必须 Function Calling？

Agent 节点核心能力是自主调用工具。Function Calling 是模型理解何时及如何调用工具的关键技术。

#### 最终拼装

```
迭代 → [知识检索 → Agent] → LLM（汇总） → 输出
```

### 第 9 课：排版设计师（模板）

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-09

#### 问题

每封邮件输出格式不统一，需要一个专属排版小助手统一格式。

#### 模板转换

像排版设计师——接收输入变量，按模板重新组合输出格式统一的文本。

#### 动手实践

**1. 更新 LLM 节点**：只专注于回答问题本身，不含问候语和落款。

```
Combine all answers for the original email. Write a complete, clear, and friendly reply that only includes the summarized answers.

IMPORTANT: Focus SOLELY on the answers. Do NOT include greetings (like "Hi Name"), do NOT write intro paragraphs (like "Thank you for reaching out"), and do NOT include signatures.
```

**2. 添加模板转换节点**，设置输入变量：
- `customer` ← `User Input / customer_name`
- `body` ← `LLM / text`

**3. Jinja2 语法排版**：

```jinja2
Hi {{ customer }},

Thank you for reaching out to us, and we are more than happy to provide you with the information you are seeking.

Here are the details regarding your specific questions:

{{ body }}

---
Thank you for reaching out to us!
Best regards,
Anne
```

#### 什么是 Jinja2？

用简单符号 `{{ }}` 标记变量位置，将原始数据列表转换为格式整齐的文本。

#### 最终工作流

```
开始 → 参数提取 → 迭代 → [知识检索 → Agent] → LLM（只有答案） → 模板转换 → 输出
```

### 第 10 课：发布和监控你的 AI 应用

> 地址：https://docs.dify.ai/zh/use-dify/tutorials/workflow-101/lesson-10

#### 发布

1. 画布右上角 **发布** 按钮
2. 点击 **发布更新**（不更新则线上保持旧版本）
3. **运行** → 获得 WebApp 链接（可分享，对方无需 Dify 账号）

#### 分享方式

| 方式 | 说明 |
|------|------|
| 运行（WebApp） | 生成网页版应用界面，分享链接即可 |
| 批量运行 | 上传 CSV 表格，一次性批量处理（可下载模板） |
| 访问 API | 获取 API 密钥，集成到自己网站或 App |
| 在"探索"中打开 | 放置到探索页面左侧工作区，快速使用 |
| 发布为工具 | 打包成插件，供其他 Agent 调用 |

#### 监测（Monitor）

图表面板，用于了解应用健康状况：

| 指标 | 释义 |
|------|------|
| 全部消息数 | AI 每天互动总次数 |
| 活跃用户数 | 有效互动（一问一答以上）的唯一用户数 |
| 费用消耗 | 每日 Token 花费，用于成本控制 |
| 平均用户调用次数 | 反映用户粘性 |

#### 日志（Logs）

每次运行的详细记录。

**日志的作用**：

| 用途 | 说明 |
|------|------|
| 排查故障 (Debug) | 还原案发现场，定位问题节点 |
| 优化性能 | 查看每个节点的耗时，找瓶颈 |
| 理解用户 | 看用户实际输入，优化 Prompt 或知识库 |
| 监控成本 | 查看每次 Token 消耗 |

**日志字段**：

| 字段 | 释义 |
|------|------|
| 开始时间 | 任务触发时间 |
| 状态 | Success（成功）/ Failure（失败） |
| 运行时间 | 整个流程耗时 |
| TOKENS | Token 消耗数 |
| 用户或账户 | 用户 ID |
| 触发方式 | WebApp 或 API |

#### LLMOps 核心理念

发布不是终点，而是新起点：

```
观察 (Observe) → 分析 (Analyze) → 优化 (Optimize) → 发布 (Publish) → 循环
```

#### 结束语

构建 AI 应用的思维方式：
```
任务拆解 → 选择合适节点/模型/工具 → 连接在一起 → 通过监测数据持续迭代
```
