# Review 评论分诊

收到 review 评论后先分诊，再决定是否改代码。**禁止“评论说什么就改什么”**。reviewer 可能基于不完整上下文，也可能提出超出本工单范围或过度设计的建议；先质疑，再用证据决定接受、部分接受、另开票或拒绝。

## 分诊表

| 评论 | 事实是否正确 | 是否本工单范围 | 是否过度设计 | 决定 |
|---|---|---|---|---|
| ... | 已复现 / 已证伪 / 无法验证 | 本工单 / 历史问题 / 其他模块 | 是 / 否 | 接受 / 部分接受 / 另开票 / 拒绝（附证据） |

## 分诊顺序

1. **事实核验**：用代码、测试、日志、复现证明评论是否成立。不成立时准备证据回复，不盲改。
2. **范围判断**：是否由本次改动引入、是否本工单验收所需。历史问题或其他模块问题 → 另开票或注明后续，不扩大本 MR diff。
3. **过度设计判断**：建议是否超出工单必要范围、是否显著增加复杂度或维护成本。是 → 提出更小替代方案，并请 reviewer 确认是否属于合并阻塞项。
4. **方案对抗**：是否存在更简单的实现。先给方案，再动手。
5. **决定与闭环**：
   - **接受**：改代码 + 补副作用 / 负向 / 异常传播断言
   - **部分接受**：说明保留与不采纳的点及理由
   - **另开票**：回复 issue / 工单链接，本 MR 不做
   - **拒绝**：引用 `file:line`、测试或日志证据，说明为什么不改，并请 reviewer 确认
6. **不 resolve reviewer 的 discussion**：由 reviewer resolve。
7. **与工单范围冲突或影响验收时**：先问用户再改。

## 原则

- 先质疑 ≠ 对抗。回复必须带证据，不静默忽略。
- 评论属于历史问题但会阻塞本工单验证时，说明依赖关系，由用户决定是否纳入本工单。
- P1 / P2 阻塞项优先处理；P3 且超出范围的建议默认另开票，不为“顺手”扩大 diff。
- 接受后必须回归验证；拒绝后必须留下可复查的依据。
