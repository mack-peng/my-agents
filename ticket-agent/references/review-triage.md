# Review 评论分诊

这是 ticket-agent 处理工单 review 反馈的通用规则，适用于各工单来源、代码仓库和 reviewer。Reviewer 可能使用其他版本的 code-review-agent、自定义规则，或人工评审。ticket-agent 独立核验每条反馈。code-agent 处理工单 review 的代码验证或修复时，复用这里的分诊判据。

## 分诊表

| 评论 | 事实与证据 | 本次 MR 对触发条件、影响面或验收的影响 | 建议改动的风险与范围 | 决定 |
|---|---|---|---|---|
| ... | 已证实 / 已证伪 / 无法验证 | 引入 / 触发或放大 / 验收所需 / 无影响 / 待核验 | 涉及的现有调用方与行为 | 本 MR 修复 / 部分采纳 / 超出范围 / 事实不成立 / 暂待证据 |

## 分诊顺序

1. **事实核验**：用代码、测试、日志或复现核验评论。需要追踪调用链时优先用项目已有的 CodeGraph。区分理论触发、生产可达和实际发生。已证伪则带证据回复事实不成立。证据不足则说明要核验的输入、调用路径或环境，保留待核验结论。
2. **范围判断**：以 MR diff 的基线和已确认的验收目标为准，对比同一输入和执行路径。检查本次改动是否引入问题、改变存量问题的触发条件或影响面，或影响验收。评论所在文件提供定位信息。确认问题成立、本次改动对它无影响且与验收无关时，说明依据后回复「超出本工单范围，不做处理」。
3. **最小修复**：对本次改动引入、触发或放大的问题，以及验收所需的改动，选择满足验收且影响最小的方案并回归验证。需要扩大或缩小已确认的交付范围、调整验收标准，或改动其他已在生产运行的共享路径时，先说明依赖关系、影响面和风险，由用户确认。同一条评论同时包含必要修复和额外建议时，说明采纳的部分及理由。
4. **存量问题的后续处理**：当前工作优先，超出范围的存量问题默认回复后结束，无需开票或排期。只有生产相关证据和实际影响足以支持跟进、且工作人员有余力并决定跟进时，才在获得授权后另开工单，并在回复中附上链接。仅有理论触发场景、当前工作量较大或余力未知时，到此为止。
5. **讨论收尾**：在原 discussion 回复证据与处置结论，由 reviewer resolve。追加 commit 后重新请求 review，并提示对比 version diff。只有回复、没有代码修改时，如果 reviewer 仍将评论标为阻塞，带上核验依据请其确认是否仍阻塞合并。若对方的流程无法仅凭证据回复触发复审，或复核后仍有分歧，记录评论、核验证据和平台上的阻塞状态，交由用户决定如何协调。代码修改仍按第 3 步的范围与验收要求判断。

## 原则

- 先质疑 ≠ 对抗。回复必须带证据，不静默忽略。
- Reviewer 标注的优先级供分诊参考。是否阻塞当前 MR 以实际影响本次改动或工单验收的证据为准。
